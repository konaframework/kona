**kona-testing** est le harnais de test des applications Kona. Il démarre une vraie `Application` sous un chemin de base temporaire, puis pilote HTTP, grind, la base de données et des factices en mémoire sans ouvrir de sockets ni toucher les services de production.

Ajoutez-le comme dépendance de test :

```kotlin
dependencies {
    testImplementation("org.konaframework:kona-testing:${konaVersion}")
}
```

## Démarrer une application

`TestApplication.create(base, *providers)` est un mince enrobage de `Kona.create("--base=…").providers(…).boot()`.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
@TempDir
lateinit var base: Path

val app = TestApplication.create(
    base,
    HttpServiceProvider(),
    MyAppProvider(),
)
```

</TabItem>
<TabItem label="Java">

```java
Path base = Files.createTempDirectory("app");
Application app = TestApplication.create(
    base,
    new HttpServiceProvider(),
    new MyAppProvider()
);
```

</TabItem>
</Tabs>

Enregistrez les routes, les liaisons et le middleware dans les providers que vous passez (ou après le démarrage). Le nettoyage est en général « jeter le répertoire temporaire » — préférez des bases neuves à la réutilisation d’apps à longue durée entre les tests.

## Quoi affirmer ensuite

| Guide | Surface |
| --- | --- |
| [Tests HTTP](./http-console/) | `HttpTestClient` / `TestResponse` |
| [Tests de console](./console/) | `ConsoleTester` / `ConsoleResult` |
| [Base de données et factices](./database-fakes/) | `DatabaseTest`, `FakeMail`, `FakeQueue`, `FakeEvent`, … |

## Exemple Java

`modules/testing` livre `JavaTestingApiTest` — les mêmes API sont `@JvmStatic` / appelables depuis Java. Préférez les exemples Kotlin ci-dessus ; appelez les mêmes types depuis Java lorsque vos tests d’app sont d’abord en Java.
