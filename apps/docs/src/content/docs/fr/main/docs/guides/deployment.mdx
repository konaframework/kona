Cette page est le **runbook de production** d’une app créée avec `kona new`. Le développement local reste sur [Votre première application](../first-app/) (`./grind serve`). La production est un lanceur différent : un processus JVM longue durée qui démarre `bootstrap.App` et écoute sur `HOST`:`PORT`.

**Chemin préféré sur une VM :** systemd. Une commande grind construit un répertoire prêt pour la production ; `install.sh` le copie en place, écrit l’unité et le fichier d’environnement, et démarre le service.

Pour plusieurs instances, pools de connexions, Redis et workers, continuez avec [Mise à l’échelle](../scaling/).

## Préféré : systemd en une commande

Sur une machine avec **JDK 21** (votre portable, la CI ou le serveur) :

```bash
cd hello-kona
./grind key:generate          # once; copy APP_KEY into the generated env file
./gradlew check               # optional, but run it before you ship
./grind deploy:systemd
# Vite / Inertia / Wire kits only, before deploy:systemd:
# npm ci && npm run build
```

Cela écrit :

```text
build/deploy/systemd/hello-kona/
  bin/hello-kona          # start script (from ./gradlew installDist)
  lib/                    # application JAR + dependencies
  public/                 # HTTP document root (do not ship public/hot)
  storage/                # empty writable dirs (logs, framework, app/public, database)
  hello-kona.service      # systemd unit
  hello-kona.env          # production environment (APP_ENV, HOST, PORT, DB_*, …)
  install.sh              # copies the tree, installs the unit, starts the service
  README.txt
```

`./grind deploy:systemd` exécute `./gradlew installDist` sauf si vous passez `--skip-build`. Relisez `hello-kona.env` (surtout `APP_KEY` et `DB_*`). Copiez le répertoire sur le serveur, puis :

```bash
sudo ./install.sh
```

Emplacements par défaut sur le serveur :

| Chemin | Quoi |
|------|------|
| `/var/www/hello-kona/bin/` | script de démarrage |
| `/var/www/hello-kona/lib/` | JARs |
| `/var/www/hello-kona/public/` | fichiers statiques |
| `/var/www/hello-kona/storage/` | runtime inscriptible (doit rester inscriptible par l’utilisateur du service) |
| `/etc/kona/hello-kona.env` | environnement (mode `0600` ; `install.sh` n’écrasera pas un fichier existant) |
| `/etc/systemd/system/hello-kona.service` | unité |

`install.sh` crée l’utilisateur système `kona` s’il manque, exécute `systemctl enable --now hello-kona`, et affiche le statut. Sondez le processus :

```bash
curl -fsS http://127.0.0.1:4000/api/health
# {"status":"ok"}
```

Depuis un checkout qui a encore `./grind`, exécutez les migrations avec les mêmes valeurs `DB_*` **avant** ou au moment où vous ouvrez le trafic :

```bash
./grind migrate --force
```

Remplacez `hello-kona` par le nom de répertoire passé à `kona new` (`rootProject.name`).

## Étapes de build (ce que fait la commande)

1. **Trouver la racine de l’application** (même remontée que `./grind serve` : `settings.gradle.kts` / `build.gradle.kts`).
2. **Compiler un script de démarrage** avec `./gradlew installDist` → `build/install/<app>/{bin,lib}`.
3. **Assembler le bundle** sous `build/deploy/systemd/<app>/` :
   - copier `bin/` et `lib/`
   - copier `public/` (ignore `public/hot` et les symlinks comme `public/storage`)
   - créer des `storage/{logs,framework,app/public,database}` vides
   - écrire `<app>.env` à partir de `.env` (ou `.env.example`) avec un overlay de production
   - écrire `<app>.service` avec `ExecStart=/var/www/<app>/bin/<app> --base=/var/www/<app>`
   - écrire `install.sh` (exécutable) et `README.txt`
4. **Vous** relisez le fichier d’env, copiez le bundle, exécutez `sudo ./install.sh`.

`--base=` est la façon dont `Kona.create` localise `public/`, `storage/` et la config. L’unité le passe toujours pour que le répertoire de travail et les fichiers restent alignés.

### Drapeaux

```bash
./grind deploy:systemd
./grind deploy:systemd --skip-build          # reuse an existing installDist tree
./grind deploy:systemd --force               # overwrite the output directory
./grind deploy:systemd --output=/tmp/hello-kona
./grind deploy:systemd --prefix=/opt/hello-kona
./grind deploy:systemd --user=www --group=www
./grind deploy:systemd --host=127.0.0.1 --port=4000
./grind deploy:systemd --url=https://app.example.com
./grind deploy:systemd --name=hello-kona
./grind deploy:systemd --java-opts='-XX:+UseG1GC -XX:MaxRAMPercentage=75.0'
```

| Drapeau | Défaut | Effet |
|------|---------|--------|
| `--skip-build` | désactivé | Ne pas exécuter `installDist` |
| `--force` | désactivé | Remplacer `build/deploy/systemd/<app>/` s’il existe déjà |
| `--output=` | `build/deploy/systemd/<app>` | Répertoire du bundle |
| `--prefix=` | `/var/www/<app>` | Racine d’installation serveur (`WorkingDirectory` / `--base`) |
| `--user=` / `--group=` | `kona` | `User` / `Group` systemd (`install.sh` crée l’utilisateur) |
| `--host=` / `--port=` | depuis `.env`, sinon `127.0.0.1`:`4000` | Adresse de bind écrite dans le fichier d’env |
| `--url=` | depuis `.env`, sinon `http://<host>:<port>` | `APP_URL` |
| `--name=` | `rootProject.name` | Nom de l’unité, du fichier d’env et du répertoire |
| `--java-opts=` | G1 + `MaxRAMPercentage=75` | `JAVA_OPTS` sur l’unité |
| `--base=` | répertoire courant | Racine d’application depuis laquelle chercher vers le haut |

Surchargez les destinations d’installation à l’exécution :

```bash
sudo PREFIX=/opt/hello-kona ENV_DST=/etc/kona/hello-kona.env UNIT_DST=/etc/systemd/system/hello-kona.service ./install.sh
```

Les apps Java utilisent la même commande (`./grind deploy:systemd` depuis un arbre `kona new --lang=java`).

## L’unité et le fichier d’env

`install.sh` installe cette forme (générée ; les noms suivent `--name`) :

`/etc/kona/hello-kona.env` :

```bash
APP_ENV=production
APP_DEBUG=false
APP_URL=https://app.example.com
APP_KEY=base64:…
HOST=127.0.0.1
PORT=4000
LOG_TO_FILE=true
DB_URL=jdbc:postgresql://127.0.0.1:5432/kona
DB_USERNAME=kona
DB_PASSWORD=…
JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
```

`/etc/systemd/system/hello-kona.service` :

```ini
[Unit]
Description=Kona hello-kona
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kona
Group=kona
WorkingDirectory=/var/www/hello-kona
EnvironmentFile=/etc/kona/hello-kona.env
Environment=JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
ExecStart=/var/www/hello-kona/bin/hello-kona --base=/var/www/hello-kona
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGTERM
LimitNOFILE=65535
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload          # install.sh already does this
sudo systemctl enable --now hello-kona
sudo systemctl status hello-kona
sudo journalctl -u hello-kona -f
```

`install.sh` **n’écrase pas** `/etc/kona/hello-kona.env` si ce fichier existe déjà, donc un second déploiement conserve les secrets de production. Les nouvelles clés vont toujours dans le `hello-kona.env` du bundle pour que vous les fusionniez à la main.

## Local vs production

| | Local | Production |
|---|--------|------------|
| Commande | `./grind serve` | `bin/<app> --base=<prefix>` (`ExecStart` systemd) |
| `APP_ENV` | `local` | `production` |
| `APP_DEBUG` | `true` | `false` |
| Base de données | Fichier SQLite sous `storage/` (défaut de l’échafaudage) | PostgreSQL, MySQL, MariaDB, SQL Server ou Oracle — pas SQLite/H2 |
| Gestionnaire de processus | votre terminal | **systemd** (préféré) ; Docker ou une plateforme qui pose `PORT` |
| TLS | optionnel | reverse proxy / load balancer |

`./grind` reste l’outil pour les **ops ponctuelles** sur un checkout (`migrate`, `key:generate`, `deploy:systemd`). Ce n’est pas le processus HTTP que vous supervisez.

## Variables d’environnement

L’environnement du processus gagne sur un fichier `.env`. systemd injecte `/etc/kona/<app>.env` via `EnvironmentFile`, donc le fichier **est** l’environnement du processus. Ne le committez pas.

| Variable | Production | Notes |
|----------|------------|--------|
| `APP_ENV` | `production` | Requis pour le comportement de production |
| `APP_DEBUG` | `false` | Désactive les pages d’exception |
| `APP_KEY` | `base64:…` | Chiffrement / cookies signés. Créez-la avec `./grind key:generate` sur une machine de confiance |
| `APP_URL` | `https://app.example.com` | URL publique utilisée dans les liens |
| `HOST` | `127.0.0.1` derrière un proxy local ; `0.0.0.0` dans Docker / PaaS | Adresse de bind |
| `PORT` | `4000` ou le `PORT` de la plateforme | Port d’écoute |
| `DB_CONNECTION` | `pgsql`, `mysql`, … | Doit correspondre à `config/Database` |
| `DB_URL` | URL JDBC | Exemple : `jdbc:postgresql://db:5432/kona` |
| `DB_USERNAME` / `DB_PASSWORD` | identifiants | Préférez le fichier d’env, pas git |
| `DB_POOL_SIZE` | commencez à `10` | Taille max Hikari ; voir [Mise à l’échelle](../scaling/) |
| `LOG_LEVEL` | `info` | |
| `LOG_TO_FILE` | `true` sur les VM avec disque ; `false` quand la plateforme capture stdout | |
| `JAVA_OPTS` | G1 + 75 % RAM | Aussi posé sur l’unité |

Générez une clé :

```bash
./grind key:generate
./grind key:generate --force    # production, key already set
```

## Base de données et migrations

Pointez `DB_URL` vers une vraie base serveur. Exécutez les migrations depuis un checkout qui a encore `./grind` :

```bash
export DB_URL='jdbc:postgresql://db.internal:5432/kona'
export DB_USERNAME=kona
export DB_PASSWORD=…
./grind migrate --force
```

Découpage typique :

- **VM (systemd) :** copiez le bundle, `sudo ./install.sh`, migrez depuis la CI ou un checkout avec les mêmes `DB_*`, puis `systemctl restart <app>` si le processus tournait déjà.
- **Conteneur :** exécutez `./grind migrate` en CI (ou un job JDK one-shot) contre la base de production, puis déployez l’image.

`storage/` doit rester inscriptible par l’utilisateur du service (`install.sh` fait un `chown` du préfixe).

Liste des moteurs et URL JDBC : [Connexions de base de données](../../cadence/database/).

## Reverse proxy et TLS

La JVM parle **HTTP**. Terminez le TLS dans Caddy, nginx, Traefik ou le load balancer cloud. Liez l’app à `127.0.0.1` quand le proxy est sur le même hôte.

**Caddy** (certificats inclus) :

```text
app.example.com {
    reverse_proxy 127.0.0.1:4000
}
```

**nginx :**

```nginx
upstream kona_app {
    server 127.0.0.1:4000;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    location / {
        proxy_pass http://kona_app;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;
    }
}
```

Derrière un proxy, activez les en-têtes transmis de confiance dans `bootstrap.Middleware` pour que `APP_URL`, les redirections et l’IP client correspondent à la requête publique : `.trustProxies(at = listOf("*"))` et `.trustHosts(at = listOf("app.example.com"))` (Java : `List.of(...)`). Détails : [Kernel & server](../../http/kernel-server/).

Utilisez `HOST=0.0.0.0` quand la plateforme route vers le port du conteneur.

## Santé et fichiers statiques

```http
GET /api/health → {"status":"ok"}
```

HTTP 200 signifie que le processus est up et que le kernel a répondu. Cela **ne** vérifie **pas** la base de données. Ajoutez votre propre route de readiness si vous en avez besoin.

`GET`/`HEAD` sous `public/` (y compris `/build/assets/…` après un build de production Vite) sont servis depuis le disque. Ne livrez pas `public/hot` — `deploy:systemd` l’ignore déjà. Ce fichier sélectionne le serveur de développement Vite.

```bash
# Vite / Inertia / Wire kits, in CI or on the build machine, before deploy:systemd
npm ci && npm run build
```

## Alternative : Docker

Il n’y a pas d’image runtime Kona publiée. Utilisez un build en deux étapes dans **le dépôt de l’app**. Remplacez `hello-kona` par `rootProject.name`. Préférez systemd sur une VM que vous possédez ; utilisez ceci quand la cible est une plateforme de conteneurs.

```dockerfile
# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew installDist --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/build/install/hello-kona/ /app/
COPY --from=build /src/public /app/public
RUN mkdir -p /app/storage/logs /app/storage/framework /app/storage/app/public \
    && chown -R 65534:65534 /app/storage
ENV HOST=0.0.0.0 PORT=4000 APP_ENV=production APP_DEBUG=false LOG_TO_FILE=false
EXPOSE 4000
USER 65534:65534
CMD ["/app/bin/hello-kona", "--base=/app"]
```

```bash
docker build -t hello-kona:latest .
docker run --rm -p 4000:4000 \
  -e APP_KEY=base64:… \
  -e APP_URL=https://app.example.com \
  -e DB_URL=jdbc:postgresql://db:5432/kona \
  -e DB_USERNAME=kona \
  -e DB_PASSWORD=… \
  hello-kona:latest
```

Montez un volume sur `/app/storage` si vous avez besoin que les logs ou les disques locaux survivent aux redémarrages. Toute plateforme qui injecte `PORT` fonctionne : l’échafaudage le lit.

## CI (GitHub Actions)

Placez ceci dans le dépôt de **l’application**. L’artefact est le bundle systemd (ou `installDist` si vous n’avez besoin que de `bin/` + `lib/`).

```yaml
name: build
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
      - name: Tests
        run: ./gradlew check
      - name: systemd bundle
        run: ./grind deploy:systemd --force
      # Vite kits only:
      # - uses: actions/setup-node@v4
      #   with: { node-version: "22" }
      # - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: hello-kona-systemd
          path: build/deploy/systemd/hello-kona
```

Promouvez l’artefact, fusionnez `/etc/kona/<app>.env` si besoin, exécutez les migrations, puis `sudo ./install.sh` ou `systemctl restart <app>`.

## `installDist` manuel (sans systemd)

Si vous n’êtes pas sur systemd, le même script de démarrage est :

```bash
./gradlew installDist
./build/install/hello-kona/bin/hello-kona --base=/var/www/hello-kona
```

Livrez un zip avec `./gradlew distZip` (`build/distributions/hello-kona-<version>.zip`). Décompressez, placez `public/` et `storage/` à côté de `bin/` / `lib/`, et démarrez avec `--base=` pointant vers ce dossier.

`./gradlew run` démarre le même `main`. Préférez `installDist` ou `deploy:systemd` sur les machines longue durée.

## Liste de contrôle

1. JDK 21 en CI / sur l’hôte de build  
2. `./gradlew check` vert  
3. `./grind key:generate` (`APP_KEY` réelle)  
4. Kits Vite : `npm run build`  
5. `./grind deploy:systemd` — relisez `<app>.env` (`APP_ENV=production`, `APP_DEBUG=false`, `APP_URL`, `DB_*`)  
6. Copiez le bundle ; `sudo ./install.sh`  
7. `./grind migrate --force`  
8. Reverse proxy + `trustProxies` / `trustHosts`  
9. `GET /api/health` renvoie `{"status":"ok"}`  
10. Forte charge : [Mise à l’échelle](../scaling/)
