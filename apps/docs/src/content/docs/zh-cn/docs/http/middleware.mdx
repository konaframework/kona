import { Tabs, TabItem } from '@astrojs/starlight/components';

**中间件**是在处理函数*周围*运行的代码。它在处理函数之前看到请求，在处理函数返回之后看到响应，因此它是许多路由共享关注点的合适位置：请求 ID、认证、访问日志、计时、CORS 头，或强制响应格式。

中间件是实现 `Middleware` 接口的任何对象：

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
fun interface Middleware {
    fun handle(request: Request, next: Handler): Response
}
```

`next` 是“管线的其余部分” — 下一个中间件，或如果这是最后一个，则是路由处理函数。中间件做三件事之一：

1. **通过：** 用请求调用 `next` 并返回它的响应，可能在修改之后。
2. **短路：** 不调用 `next` 就返回 `Response`。链里更远的东西都不运行。认证中间件就是这样拒绝请求的。
3. **抛出：** 引发异常（例如 `HttpException(401, "Unauthenticated.")`）。内核的异常处理程序把它变成响应；见[异常去哪里](#where-exceptions-go)。

## 编写中间件

### 通过型中间件

这个中间件确保每个响应都携带 `X-Request-Id` 头，客户端发送了 ID 时复用它，并把它存在请求属性里，这样处理函数可以记录它。

```kotlin
import org.konaframework.http.Handler
import org.konaframework.http.Middleware
import org.konaframework.http.Request
import org.konaframework.http.Response
import org.konaframework.http.invoke
import java.util.UUID

class RequestIdMiddleware : Middleware {
    override fun handle(request: Request, next: Handler): Response {
        val id = request.header("X-Request-Id") ?: UUID.randomUUID().toString()
        request.setAttribute("requestId", id)
        val response = next(request)
        return response.header("X-Request-Id", id)
    }
}
```

</TabItem>
<TabItem label="Java">

```java
import org.konaframework.http.Handler;
import org.konaframework.http.Middleware;
import org.konaframework.http.Request;
import org.konaframework.http.Response;
import java.util.UUID;

public final class RequestIdMiddleware implements Middleware {
    @Override
    public Response handle(Request request, Handler next) {
        String id = request.header("X-Request-Id", UUID.randomUUID().toString());
        request.setAttribute("requestId", id);
        Response response = next.handle(request);
        return response.header("X-Request-Id", id);
    }
}
```

</TabItem>
</Tabs>

在 Kotlin 里，`next(request)` 是 `next.handle(request)` 的简写；文件在另一个包里时需要 `import org.konaframework.http.invoke`。两种写法做同样的事。

### 短路中间件

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class Authenticate(private val tokens: TokenStore) : Middleware {
    override fun handle(request: Request, next: Handler): Response {
        val token = request.header("Authorization")?.removePrefix("Bearer ")
        val user = token?.let(tokens::find)
            ?: return Response.json(mapOf("message" to "Unauthenticated."), 401)
        request.setAttribute("user", user)
        return next.handle(request)
    }
}
```

</TabItem>
<TabItem label="Java">

```java
public final class Authenticate implements Middleware {
    private final TokenStore tokens;

    public Authenticate(TokenStore tokens) { this.tokens = tokens; }

    @Override
    public Response handle(Request request, Handler next) {
        String header = request.header("Authorization", "");
        User user = tokens.find(header.replaceFirst("^Bearer ", ""));
        if (user == null) {
            return Response.json(Map.of("message", "Unauthenticated."), 401);
        }
        request.setAttribute("user", user);
        return next.handle(request);
    }
}
```

</TabItem>
</Tabs>

### Lambda

因为 `Middleware` 是函数式接口，小中间件可以是 lambda：

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val poweredBy = Middleware { request, next -> next.handle(request).header("X-Powered-By", "Kona") }
```

</TabItem>
<TabItem label="Java">

```java
Middleware poweredBy = (request, next) -> next.handle(request).header("X-Powered-By", "Kona");
```

</TabItem>
</Tabs>

如果稍后需要用 `hasMiddleware` 检查它，保留对 lambda 的引用；两个分开写的 lambda 永远不相等。

### 中间件可以改变什么

- **请求：** 方法、路径、头、查询和正文是只读的。用**属性**（`setAttribute` / `getAttribute`）把数据传给后面的阶段。
- **响应：** 状态、正文和头是可变的。使用 `header`、`withStatus` 和 `withBody`，或返回一个全新的 `Response`。

中间件对象被所有请求共享，请求在各自的线程上并发运行。把每次请求的数据留在局部变量或请求属性里，绝不留在中间件的字段里。

## 全局中间件

**全局中间件**属于 `HttpKernel`，对**每一个**请求运行 — 包括不匹配任何路由的请求。它包装路由、路由中间件、处理函数，以及对所有这些的异常处理。因此全局中间件看到最终的 404、405、422 或 500 响应，就像成功的一样，这正是访问日志或安全头中间件需要的。

在内核上配置它，通常来自服务提供者的 `boot` 方法：

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
override fun boot(app: Application) {
    app.resolve(HttpKernel::class.java)
        .pushMiddleware(RequestIdMiddleware())
        .pushMiddleware(AccessLogMiddleware())
        .prependMiddleware(SecurityHeaders())
}
```

</TabItem>
<TabItem label="Java">

```java
@Override
public void boot(Application app) {
    app.resolve(HttpKernel.class)
        .pushMiddleware(new RequestIdMiddleware())
        .pushMiddleware(new AccessLogMiddleware())
        .prependMiddleware(new SecurityHeaders());
}
```

</TabItem>
</Tabs>

| 方法 | 效果 |
|------|------|
| `pushMiddleware(mw)` | 加到列表末尾 — **最内层**位置。已存在则跳过。 |
| `prependMiddleware(mw)` | 加到前面 — **最外层**位置。已存在则跳过。 |
| `setGlobalMiddleware(list)` | 完全替换列表（没有重复检查）。 |
| `hasMiddleware(mw)` | `mw` 是否在列表里（用 `equals` 比较）。 |
| `globalMiddleware` / `getGlobalMiddleware()` | 当前列表。 |

你也可以在自己构造内核时传入列表：Kotlin 是 `HttpKernel(router, listOf(a, b))`，Java 是 `new HttpKernel(router, List.of(a, b))`。每个请求使用开始时取得的列表快照。

## 路由和分组中间件

**路由中间件**只在选中路由之后运行，并且只为该路由。用 `.middleware(...)` 附到一条路由，或通过分组一次附到许多路由：

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/reports") { reports.index(it) }.middleware(Authenticate(tokens), RequireRole("analyst"))

router.group(prefix = "/admin", middleware = listOf(Authenticate(tokens), RequireAdmin())) {
    get("/users") { admin.users(it) }
}
```

</TabItem>
<TabItem label="Java">

```java
router.get("/reports", reports::index).middleware(new Authenticate(tokens), new RequireRole("analyst"));

router.prefix("/admin").middleware(new Authenticate(tokens), new RequireAdmin()).group(admin ->
    admin.get("/users", adminController::users));
```

</TabItem>
</Tabs>

路由中间件对 404 响应、405 响应或自动 `OPTIONS` 回复**不**运行，因为没有选中路由。由 `GET` 路由服务的 `HEAD` 请求会运行该 `GET` 路由的中间件。

## 执行顺序

列表顺序是包装顺序：第一个中间件是最外层。对全局中间件 `[A, B]`、分组中间件 `[G]` 和路由中间件 `[R]`，请求这样流动：

```text
A before → B before → (route resolved) → G before → R before → handler
A after  ← B after  ←                    G after  ← R after  ←
```

你写在 `next` 之前的代码自上而下运行；`next` 之后的代码反向运行。嵌套分组把它们的中间件追加在外层分组之后，路由本身上的 `.middleware(...)` 最后。

## 异常去哪里

内核在两个地方捕获异常，哪一个适用会改变谁能看到错误：

- **在路由内部抛出** — 由路由器（404/405）、路由或分组中间件，或处理函数。异常首先向上穿过路由中间件，因此路由中间件可以在 `next` 周围 `try`/`catch`，如果它想恢复。如果没被捕获，内核的 `ExceptionHandler` 把它转换成响应，该响应然后正常向外穿过**所有全局中间件**。
- **由全局中间件本身抛出。** 内核在最外面捕获它并用同一个异常处理程序转换。全局中间件**看不到**这个响应，因为链已经展开过它们。

因此全局中间件从不从 `next` 收到异常 — 它总是收到 `Response`。响应格式见[异常](../exceptions/)，完整管线见[内核与服务器](../kernel-server/)。

## 可终止中间件

需要在响应完全产生**之后**工作（刷新指标、写访问日志）时实现 `TerminableMiddleware`。内核对每一个运行过的可终止中间件调用 `terminate(request, response)` — 全局先，然后路由 — 按**反向**顺序，在 HEAD 正文剥离之后。

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class AccessLog : TerminableMiddleware {
    override fun handle(request: Request, next: Handler): Response = next(request)

    override fun terminate(request: Request, response: Response) {
        Log.info("${request.method} ${request.path} → ${response.status}")
    }
}
```

</TabItem>
<TabItem label="Java">

```java
public final class AccessLog implements TerminableMiddleware {
    @Override
    public Response handle(Request request, Handler next) {
        return next.handle(request);
    }

    @Override
    public void terminate(Request request, Response response) {
        Log.info(request.getMethod() + " " + request.getPath() + " → " + response.getStatus());
    }
}
```

</TabItem>
</Tabs>

## 优先级

`HttpKernel.priority(PreferFirst.class, PreferSecond.class)` 重排**全局**中间件列表，使列出的类型更早运行（最外层）。未列出的中间件在优先的那些之后保持相对顺序。路由中间件不被优先级重排。

## 测试中间件

`MiddlewarePipeline.pipe(middlewares, destination)` 构建内核使用的同一条链，这让你可以隔离测试中间件：

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val handler = MiddlewarePipeline.pipe(listOf(RequestIdMiddleware())) { Response.text("ok") }
val response = handler.handle(Request.get("/"))
check(response.headers.containsKey("X-Request-Id"))
```

</TabItem>
<TabItem label="Java">

```java
Handler handler = MiddlewarePipeline.pipe(List.of(new RequestIdMiddleware()), request -> Response.text("ok"));
Response response = handler.handle(Request.get("/"));
assert response.getHeaders().containsKey("X-Request-Id");
```

</TabItem>
</Tabs>

## 用 `HttpMiddleware` 引导

来自 `kona new` 的应用在 `bootstrap.Middleware.configure(app)` 里配置中间件。该辅助方法使用 `HttpMiddleware` — **别名**、**`web`** 栈（推到全局内核上）、可选的 **`api`** 栈（用于路由分组），以及可选的**信任**中间件的登记器。

典型脚手架（简化）：

```kotlin
object Middleware {
    @JvmStatic
    fun configure(app: Application) {
        val sessions = app.resolve(SessionManager::class.java)
        val files = app.resolve(FilesystemManager::class.java)
        app.resolve(HttpKernel::class.java)
            .prependMiddleware(ServePublicStorage(files.disk("public")))
        HttpMiddleware()
            .alias("start.session") { StartSession(sessions) }
            .alias("csrf") { VerifyCsrfToken(except = listOf("/api/*", "/wire/*")) }
            .web(listOf("start.session", "csrf"))
            // .trustProxies(at = listOf("*"))
            // .trustHosts(at = listOf("example.com", "*.example.com"))
            .apply(app)
    }
}
```

| 方法 | 作用 |
|------|------|
| `alias(name, factory)` | 登记具名中间件供应者 |
| `web(prepend, append)` / `api(...)` | 用别名替换具名栈 |
| `webStack()` / `apiStack()` | 把别名解析成中间件实例 |
| `trustProxies(at, headers)` | 在 `apply` 上前置 `TrustProxies` |
| `trustHosts(at)` | 在 `apply` 上前置 `TrustHosts` |
| `apply(app)` | 前置信任中间件，把 `web` 栈推到 `HttpKernel` 上，把该登记器绑定进容器 |

**`api` 栈不全局应用** — 当你想要自己设计的无会话 JSON 中间件时，解析 `apiStack()` 并把它传给路由分组。

用 [`./grind make:middleware Name`](../../grind/commands/#grind-makemiddleware) 生成桩。

## 值得知道的内置中间件

| 类型 | 模块 | 作用 |
|------|------|------|
| `StartSession` | session | 加载/保存会话；闪存；上一个 URL |
| `VerifyCsrfToken` | session | 拒绝伪造的表单提交；`except` 路径模式 |
| `ServePublicStorage` | http | 在 `/storage/...` 下服务公开磁盘文件 |
| `TrustProxies` | http | 对等方受信任时把 `X-Forwarded-*` / `X-Real-IP` 复制到请求属性 |
| `TrustHosts` | http | 用 **400** 拒绝未知的 `Host` 头 |
| `ValidateSignature` | http | 要求有效的签名查询字符串（[URL 生成](../url-generation/)） |
| `CorsMiddleware` | auth/security | CORS 头 |
| `SecurityHeadersMiddleware` | auth/security | 安全响应头 |

`TrustProxies` 设置 `kona.clientIp`、`kona.scheme`、`kona.host`、`kona.port` 等属性。`Request.ip()` 先读 `kona.clientIp` 再读 `kona.remoteAddr`。CSRF 和会话细节见[安全](../../security/)指南。

| 类型 | 作用 |
|------|------|
| `Middleware` | `handle(request, next): Response` |
| `TerminableMiddleware` | 外加响应产生之后的 `terminate(request, response)` |
| `MiddlewarePipeline.pipe` | 为测试或自定义派发构建链 |
| `MiddlewarePipeline.sortByPriority` | 按类型列表重排 |

## 陷阱与常见问题

**为什么我的路由中间件不在 404 上运行？**  
没有选中路由。必须看到未命中的访问日志使用全局中间件。

**为什么我的中间件运行两次？**  
`pushMiddleware` 按 `equals` 跳过重复；lambda 永远不等于先前的 lambda。优先使用具名类。

**我可以在路由上按字符串别名附加中间件吗？**  
今天在 `Route.middleware(...)` 上不行 — 传入实例。别名用于 `HttpMiddleware` 栈。

**方法伪装（`_method`）住在这里吗？**  
不。Crema 可以在 HTML 里发出隐藏的 `_method` 字段，但内核今天不会从该字段重写 HTTP 方法 — 见 [Crema 表单](../../crema/forms/#method-spoofing)。

## 今天不可用的内容

- 单个 `Route.middleware("auth")` 调用上的字符串中间件别名
- 自动的 `_method` 覆盖中间件
- 超出你用 `HttpMiddleware` 加路由 `group(...)` 构建的中间件分组
- 协程 / 响应式中间件 API（处理函数在虚拟线程上阻塞）
