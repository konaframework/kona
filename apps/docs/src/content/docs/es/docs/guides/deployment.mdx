Esta página es el **runbook de producción** de una app creada con `kona new`. El desarrollo local se queda en [Tu primera app](../first-app/) (`./grind serve`). Producción es un lanzador distinto: un proceso JVM de larga duración que arranca `bootstrap.App` y escucha en `HOST`:`PORT`.

**Camino preferido en una VM:** systemd. Un comando grind construye un directorio listo para producción; `install.sh` lo copia en su sitio, escribe la unidad y el archivo de entorno, y arranca el servicio.

Para muchas instancias, pools de conexión, Redis y workers, continúa con [Escalado](../scaling/).

## Preferido: systemd en un comando

En una máquina con **JDK 21** (tu portátil, CI o el servidor):

```bash
cd hello-kona
./grind key:generate          # once; copy APP_KEY into the generated env file
./gradlew check               # optional, but run it before you ship
./grind deploy:systemd
# Vite / Inertia / Wire kits only, before deploy:systemd:
# npm ci && npm run build
```

Eso escribe:

```text
build/deploy/systemd/hello-kona/
  bin/hello-kona          # start script (from ./gradlew installDist)
  lib/                    # application JAR + dependencies
  public/                 # HTTP document root (do not ship public/hot)
  storage/                # empty writable dirs (logs, framework, app/public, database)
  hello-kona.service      # systemd unit
  hello-kona.env          # production environment (APP_ENV, HOST, PORT, DB_*, …)
  install.sh              # copies the tree, installs the unit, starts the service
  README.txt
```

`./grind deploy:systemd` ejecuta `./gradlew installDist` salvo que pases `--skip-build`. Revisa `hello-kona.env` (sobre todo `APP_KEY` y `DB_*`). Copia el directorio al servidor y luego:

```bash
sudo ./install.sh
```

Ubicaciones predeterminadas en el servidor:

| Camino | Qué |
|------|------|
| `/var/www/hello-kona/bin/` | script de arranque |
| `/var/www/hello-kona/lib/` | JARs |
| `/var/www/hello-kona/public/` | archivos estáticos |
| `/var/www/hello-kona/storage/` | runtime escribible (debe seguir siendo escribible por el usuario del servicio) |
| `/etc/kona/hello-kona.env` | entorno (modo `0600`; `install.sh` no sobrescribirá un archivo existente) |
| `/etc/systemd/system/hello-kona.service` | unidad |

`install.sh` crea el usuario de sistema `kona` si falta, ejecuta `systemctl enable --now hello-kona` e imprime el estado. Sonda el proceso:

```bash
curl -fsS http://127.0.0.1:4000/api/health
# {"status":"ok"}
```

Desde un checkout que aún tenga `./grind`, ejecuta las migraciones contra los mismos valores `DB_*` **antes** o mientras empiezas el tráfico:

```bash
./grind migrate --force
```

Sustituye `hello-kona` por el nombre de directorio que pasaste a `kona new` (`rootProject.name`).

## Pasos del build (lo que hace el comando)

1. **Encuentra la raíz de la aplicación** (el mismo recorrido que `./grind serve`: `settings.gradle.kts` / `build.gradle.kts`).
2. **Compila un script de arranque** con `./gradlew installDist` → `build/install/<app>/{bin,lib}`.
3. **Arma el paquete** bajo `build/deploy/systemd/<app>/`:
   - copia `bin/` y `lib/`
   - copia `public/` (salta `public/hot` y enlaces simbólicos como `public/storage`)
   - crea `storage/{logs,framework,app/public,database}` vacíos
   - escribe `<app>.env` a partir de `.env` (o `.env.example`) con una superposición de producción
   - escribe `<app>.service` con `ExecStart=/var/www/<app>/bin/<app> --base=/var/www/<app>`
   - escribe `install.sh` (ejecutable) y `README.txt`
4. **Tú** revisas el archivo de entorno, copias el paquete y ejecutas `sudo ./install.sh`.

`--base=` es cómo `Kona.create` localiza `public/`, `storage/` y la configuración. La unidad siempre lo pasa para que el directorio de trabajo y los archivos sigan alineados.

### Banderas

```bash
./grind deploy:systemd
./grind deploy:systemd --skip-build          # reuse an existing installDist tree
./grind deploy:systemd --force               # overwrite the output directory
./grind deploy:systemd --output=/tmp/hello-kona
./grind deploy:systemd --prefix=/opt/hello-kona
./grind deploy:systemd --user=www --group=www
./grind deploy:systemd --host=127.0.0.1 --port=4000
./grind deploy:systemd --url=https://app.example.com
./grind deploy:systemd --name=hello-kona
./grind deploy:systemd --java-opts='-XX:+UseG1GC -XX:MaxRAMPercentage=75.0'
```

| Bandera | Predeterminado | Efecto |
|------|---------|--------|
| `--skip-build` | apagado | No ejecuta `installDist` |
| `--force` | apagado | Sustituye `build/deploy/systemd/<app>/` si ya existe |
| `--output=` | `build/deploy/systemd/<app>` | Directorio del paquete |
| `--prefix=` | `/var/www/<app>` | Raíz de instalación del servidor (`WorkingDirectory` / `--base`) |
| `--user=` / `--group=` | `kona` | `User` / `Group` de systemd (`install.sh` crea el usuario) |
| `--host=` / `--port=` | de `.env`, si no `127.0.0.1`:`4000` | Dirección de bind escrita en el archivo de entorno |
| `--url=` | de `.env`, si no `http://<host>:<port>` | `APP_URL` |
| `--name=` | `rootProject.name` | Nombre de la unidad, del archivo de entorno y del directorio |
| `--java-opts=` | G1 + `MaxRAMPercentage=75` | `JAVA_OPTS` en la unidad |
| `--base=` | directorio actual | Raíz de la aplicación desde la que buscar hacia arriba |

Anula los destinos de instalación en tiempo de ejecución:

```bash
sudo PREFIX=/opt/hello-kona ENV_DST=/etc/kona/hello-kona.env UNIT_DST=/etc/systemd/system/hello-kona.service ./install.sh
```

Las apps Java usan el mismo comando (`./grind deploy:systemd` desde un árbol `kona new --lang=java`).

## La unidad y el archivo de entorno

`install.sh` instala esta forma (generada; los nombres siguen `--name`):

`/etc/kona/hello-kona.env`:

```bash
APP_ENV=production
APP_DEBUG=false
APP_URL=https://app.example.com
APP_KEY=base64:…
HOST=127.0.0.1
PORT=4000
LOG_TO_FILE=true
DB_URL=jdbc:postgresql://127.0.0.1:5432/kona
DB_USERNAME=kona
DB_PASSWORD=…
JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
```

`/etc/systemd/system/hello-kona.service`:

```ini
[Unit]
Description=Kona hello-kona
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kona
Group=kona
WorkingDirectory=/var/www/hello-kona
EnvironmentFile=/etc/kona/hello-kona.env
Environment=JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
ExecStart=/var/www/hello-kona/bin/hello-kona --base=/var/www/hello-kona
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGTERM
LimitNOFILE=65535
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload          # install.sh already does this
sudo systemctl enable --now hello-kona
sudo systemctl status hello-kona
sudo journalctl -u hello-kona -f
```

`install.sh` **no** sobrescribe `/etc/kona/hello-kona.env` si ese archivo ya existe, así que un segundo despliegue conserva los secretos de producción. Las claves nuevas siguen yendo al `hello-kona.env` del paquete para que las fusiones a mano.

## Local frente a producción

| | Local | Producción |
|---|--------|------------|
| Comando | `./grind serve` | `bin/<app> --base=<prefix>` (`ExecStart` de systemd) |
| `APP_ENV` | `local` | `production` |
| `APP_DEBUG` | `true` | `false` |
| Base de datos | Archivo SQLite bajo `storage/` (predeterminado del andamiaje) | PostgreSQL, MySQL, MariaDB, SQL Server u Oracle — no SQLite/H2 |
| Gestor de procesos | tu terminal | **systemd** (preferido); Docker o una plataforma que ponga `PORT` |
| TLS | opcional | proxy inverso / balanceador de carga |

`./grind` sigue siendo la herramienta de **operaciones puntuales** en un checkout (`migrate`, `key:generate`, `deploy:systemd`). No es el proceso HTTP que supervisas.

## Variables de entorno

El entorno del proceso gana sobre un archivo `.env`. systemd inyecta `/etc/kona/<app>.env` mediante `EnvironmentFile`, así que el archivo **es** el entorno del proceso. No lo commitees.

| Variable | Producción | Notas |
|----------|------------|--------|
| `APP_ENV` | `production` | Obligatorio para el comportamiento de producción |
| `APP_DEBUG` | `false` | Apaga las páginas de excepción |
| `APP_KEY` | `base64:…` | Cifrado / cookies firmadas. Créala con `./grind key:generate` en una máquina de confianza |
| `APP_URL` | `https://app.example.com` | URL pública usada en los enlaces |
| `HOST` | `127.0.0.1` detrás de un proxy local; `0.0.0.0` en Docker / PaaS | Dirección de bind |
| `PORT` | `4000` o el `PORT` de la plataforma | Puerto de escucha |
| `DB_CONNECTION` | `pgsql`, `mysql`, … | Debe coincidir con `config/Database` |
| `DB_URL` | URL JDBC | Ejemplo: `jdbc:postgresql://db:5432/kona` |
| `DB_USERNAME` / `DB_PASSWORD` | credenciales | Prefiere el archivo de entorno, no git |
| `DB_POOL_SIZE` | empieza en `10` | Tamaño máximo de Hikari; consulta [Escalado](../scaling/) |
| `LOG_LEVEL` | `info` | |
| `LOG_TO_FILE` | `true` en VMs con disco; `false` cuando la plataforma captura stdout | |
| `JAVA_OPTS` | G1 + 75% de RAM | También se pone en la unidad |

Genera una clave:

```bash
./grind key:generate
./grind key:generate --force    # production, key already set
```

## Base de datos y migraciones

Apunta `DB_URL` a una base de datos de servidor real. Ejecuta las migraciones desde un checkout que aún tenga `./grind`:

```bash
export DB_URL='jdbc:postgresql://db.internal:5432/kona'
export DB_USERNAME=kona
export DB_PASSWORD=…
./grind migrate --force
```

División típica:

- **VM (systemd):** copia el paquete, `sudo ./install.sh`, migra desde CI o un checkout con los mismos `DB_*`, y luego `systemctl restart <app>` si el proceso ya estaba corriendo.
- **Contenedor:** ejecuta `./grind migrate` en CI (o un trabajo JDK de un solo uso) contra la base de datos de producción, y luego despliega la imagen.

`storage/` debe seguir siendo escribible por el usuario del servicio (`install.sh` hace `chown` del prefijo).

Lista de motores y URL JDBC: [Base de datos](../../cadence/database/).

## Proxy inverso y TLS

La JVM habla **HTTP**. Termina el TLS en Caddy, nginx, Traefik o el balanceador de carga de la nube. Enlaza la app a `127.0.0.1` cuando el proxy está en el mismo host.

**Caddy** (certificados incluidos):

```text
app.example.com {
    reverse_proxy 127.0.0.1:4000
}
```

**nginx:**

```nginx
upstream kona_app {
    server 127.0.0.1:4000;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    location / {
        proxy_pass http://kona_app;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;
    }
}
```

Detrás de un proxy, activa las cabeceras reenviadas de confianza en `bootstrap.Middleware` para que `APP_URL`, las redirecciones y la IP del cliente coincidan con la petición pública: `.trustProxies(at = listOf("*"))` y `.trustHosts(at = listOf("app.example.com"))` (Java: `List.of(...)`). Detalles: [Kernel y servidor](../../http/kernel-server/).

Usa `HOST=0.0.0.0` cuando la plataforma enruta al puerto del contenedor.

## Salud y archivos estáticos

```http
GET /api/health → {"status":"ok"}
```

HTTP 200 significa que el proceso está arriba y el kernel respondió. **No** comprueba la base de datos. Añade tu propia ruta de readiness si la necesitas.

`GET`/`HEAD` bajo `public/` (incluido `/build/assets/…` después de un build de producción de Vite) se sirven desde disco. No envíes `public/hot` — `deploy:systemd` ya lo salta. Ese archivo selecciona el servidor de desarrollo de Vite.

```bash
# Vite / Inertia / Wire kits, in CI or on the build machine, before deploy:systemd
npm ci && npm run build
```

## Alternativa: Docker

No hay una imagen de runtime de Kona publicada. Usa un build de dos etapas en **el repositorio de la app**. Sustituye `hello-kona` por `rootProject.name`. Prefiere systemd en una VM que poseas; usa esto cuando el destino es una plataforma de contenedores.

```dockerfile
# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew installDist --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/build/install/hello-kona/ /app/
COPY --from=build /src/public /app/public
RUN mkdir -p /app/storage/logs /app/storage/framework /app/storage/app/public \
    && chown -R 65534:65534 /app/storage
ENV HOST=0.0.0.0 PORT=4000 APP_ENV=production APP_DEBUG=false LOG_TO_FILE=false
EXPOSE 4000
USER 65534:65534
CMD ["/app/bin/hello-kona", "--base=/app"]
```

```bash
docker build -t hello-kona:latest .
docker run --rm -p 4000:4000 \
  -e APP_KEY=base64:… \
  -e APP_URL=https://app.example.com \
  -e DB_URL=jdbc:postgresql://db:5432/kona \
  -e DB_USERNAME=kona \
  -e DB_PASSWORD=… \
  hello-kona:latest
```

Monta un volumen en `/app/storage` si necesitas que los registros o los discos locales sobrevivan a los reinicios. Cualquier plataforma que inyecte `PORT` funciona: el andamiaje lo lee.

## CI (GitHub Actions)

Pon esto en el repositorio de **la aplicación**. El artefacto es el paquete systemd (o `installDist` si solo necesitas `bin/` + `lib/`).

```yaml
name: build
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
      - name: Tests
        run: ./gradlew check
      - name: systemd bundle
        run: ./grind deploy:systemd --force
      # Vite kits only:
      # - uses: actions/setup-node@v4
      #   with: { node-version: "22" }
      # - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: hello-kona-systemd
          path: build/deploy/systemd/hello-kona
```

Promociona el artefacto, fusiona `/etc/kona/<app>.env` si hace falta, ejecuta las migraciones y luego `sudo ./install.sh` o `systemctl restart <app>`.

## `installDist` manual (sin systemd)

Si no estás en systemd, el mismo script de arranque es:

```bash
./gradlew installDist
./build/install/hello-kona/bin/hello-kona --base=/var/www/hello-kona
```

Envía un zip con `./gradlew distZip` (`build/distributions/hello-kona-<version>.zip`). Desempaqueta, coloca `public/` y `storage/` junto a `bin/` / `lib/`, y arranca con `--base=` apuntando a esa carpeta.

`./gradlew run` arranca el mismo `main`. Prefiere `installDist` o `deploy:systemd` en máquinas de larga duración.

## Lista

1. JDK 21 en CI / en el host de build
2. `./gradlew check` en verde
3. `./grind key:generate` (`APP_KEY` real)
4. Kits Vite: `npm run build`
5. `./grind deploy:systemd` — revisa `<app>.env` (`APP_ENV=production`, `APP_DEBUG=false`, `APP_URL`, `DB_*`)
6. Copia el paquete; `sudo ./install.sh`
7. `./grind migrate --force`
8. Proxy inverso + `trustProxies` / `trustHosts`
9. `GET /api/health` devuelve `{"status":"ok"}`
10. Carga fuerte: [Escalado](../scaling/)
