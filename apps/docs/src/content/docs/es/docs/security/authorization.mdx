Authorization answers: *may this user do that?* After authentication identifies the user, gates and policies decide abilities.

## Simple path

1. Resolve `Gate` from the container (registered by `AuthServiceProvider`) or construct one.
2. Point the gate at the current user with `setUserResolver { auth.user() }`.
3. `define` abilities or `policy` model classes; call `allows` / `authorize` in handlers or mount `Authorize` middleware.

```kotlin
gate.define("edit-post") { user, args ->
    val post = args.firstOrNull() as? Post ?: return@define false
    user?.getAuthIdentifier() == post.ownerId
}
if (gate.allows("edit-post", post)) { /* … */ }
gate.authorize("edit-post", post) // throws AuthorizationException (403)
```

```java
gate.define("edit-post", (user, args) -> {
    if (args.length == 0 || !(args[0] instanceof Post post)) return false;
    return user != null && user.getAuthIdentifier().equals(post.ownerId);
});
gate.authorize("edit-post", post);
```

## Gate API

| Method | Behavior |
|--------|----------|
| `define` | Register a named ability callback |
| `allows` / `denies` | Boolean check (current user or explicit user) |
| `any` / `none` | Combine several ability names |
| `authorize` | Throw `AuthorizationException` when denied |
| `before` | Global short-circuit (`null` continues; `true`/`false` settles) |
| `policy` | Bind a `Policy` to a model class |
| `discoverPolicy` | Load `{SimpleName}Policy` from a package by convention |
| `forUser` | Scoped inspector (`allows` / `any` / `authorize` for one user) |
| `has` | Whether an ability name is defined |
| `setDefault` / `getDefault` | Process-wide gate used by `Authorizable` |

```kotlin
gate.before { user, ability, _ ->
    if (user is Admin) true else null
}
gate.any(listOf("edit", "publish"), post)
gate.none(listOf("delete"), post)
```

## Policies

Register a policy for a model class. Ability checks pass either a **model instance** (`update`, `view`, `delete`) or the **model class** (`viewAny`, `create`, `deleteAny`).

```kotlin
gate.policy(Post::class.java, PostPolicy())

gate.allows("viewAny", Post::class.java)   // class-level
gate.allows("create", Post::class.java)
gate.allows("update", post)                // instance
```

Prefer **ability-named methods** on the policy. The gate looks up a method matching the ability (kebab/snake names become camelCase: `view-any` → `viewAny`), runs `before`, then falls back to `authorizeClass` / `authorize`.

```kotlin
class PostPolicy : Policy {
    override fun before(user: Authenticatable?, ability: String): Boolean? =
        if (user is Admin) true else null

    fun viewAny(user: Authenticatable?): Boolean =
        user != null

    fun create(user: Authenticatable?): Boolean =
        user != null

    fun update(user: Authenticatable?, post: Post): Boolean =
        user?.getAuthIdentifier() == post.ownerId

    override fun authorize(user: Authenticatable?, ability: String, model: Any): Boolean =
        false
}
```

```java
public class PostPolicy implements Policy {
    public boolean viewAny(Authenticatable user) {
        return user != null;
    }

    public boolean create(Authenticatable user) {
        return user != null;
    }

    public boolean update(Authenticatable user, Post post) {
        return user != null && user.getAuthIdentifier().equals(post.ownerId);
    }

    @Override
    public boolean authorize(Authenticatable user, String ability, Object model) {
        return false;
    }
}
```

When the first argument is a `Class`, Kona resolves the policy for **that** class (not `java.lang.Class`). Class arguments used only for lookup are omitted when the policy method takes only the user (as with `create` / `viewAny`). Override `authorizeClass` when you need a fallback without a named method.

Convention discovery:

```kotlin
gate.discoverPolicy(Post::class.java, "app.policies") // loads app.policies.PostPolicy
```

Generate a stub with grind:

```bash
./grind make:policy Post --model=Post
./grind make:policy CommentPolicy --lang=java
```

## Authorizable users

Implement `Authorizable` on user models for `can` / `cannot` / `canAny`. Defaults use `Gate.getDefault()` (set when `AuthServiceProvider` boots).

```kotlin
class User(...) : Authenticatable, Authorizable {
    // authorizableGate() defaults to Gate.getDefault()
}

if (user.can("create", Post::class.java)) { /* … */ }
if (user.cannot("update", post)) { /* … */ }
if (user.canAny(listOf("publish", "edit"), post)) { /* … */ }
```

```java
public class User implements Authenticatable, Authorizable {
    // ...
}

user.can("create", Post.class);
user.cannot("update", post);
user.canAny(List.of("publish", "edit"), post);
```

Override `authorizableGate()` when a user must target a specific `Gate` instance instead of the default.

## Authorize middleware

```kotlin
router.put("/posts/{id}", handler).middleware(
    Authorize(gate, "update") { request ->
        arrayOf(Post.find(request.route("id")!!))
    },
)

// Class-level: create / viewAny against the model type
router.post("/posts", handler).middleware(
    Authorize(gate, "create", Post::class.java),
)
```

```java
router.post("/posts", handler).middleware(
    new Authorize(gate, "create", Post.class)
);
```

Denied checks throw `AuthorizationException` (HTTP 403).

## Crema templates

In views, pass abilities via `__abilities` or a `can` map and use `@can` / `@cannot` (see [Crema control structures](/docs/crema/control-structures/)). Template checks are data-driven — they do not call `Gate` automatically.
