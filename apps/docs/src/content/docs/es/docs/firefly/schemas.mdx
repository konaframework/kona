Un esquema es el árbol que construyes en lugar de escribir el HTML de la página a mano. Las secciones, el texto y, más tarde, los campos y los botones se sientan en ese árbol. Llenas el mapa de estado y luego `render()` devuelve HTML. Las piezas vivas se enlazan con `wire:model` y `@entangle`.

Usas un esquema siempre que una pantalla es más que un control. La página Desk es un esquema de un campo de nombre, un campo de estado y un campo de vencimiento, más un infolist y una tabla al lado. Los tipos viven en `org.konaframework.firefly.schemas` (`kona-firefly-schemas`).

## Un esquema en una llamada

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val schema = Schema.make()
    .statePath("user")
    .components(
        Section.make("Profile").schema(
            Text.make("Hello"),
        ),
    )
schema.hydrate()
val html = schema.render()
```

</TabItem>
<TabItem label="Java">

```java
Schema schema = Schema.make()
    .statePath("user")
    .components(Section.make("Profile").schema(Text.make("Hello")));
schema.hydrate();
String html = schema.render();
```

</TabItem>
</Tabs>

`Schema.make()` empieza un árbol vacío. `statePath("user")` prefija cada componente raíz, así que un campo llamado `name` se guarda en `user.name`. `components(...)` sustituye la lista raíz y enlaza cada componente al esquema. `hydrate()` escribe los predeterminados en los caminos ausentes. `render()` devuelve un `<div class="ff-schema">`.

`get` y `set` usan caminos con puntos. `set` devuelve las claves de render parcial de esa actualización. Un componente que llamó a `live()`, `liveOnBlur()` o `liveDebounce(...)` aporta su propio camino.

## Valores y cierres

La mayoría de los setters encadenables aceptan un valor fijo o un cierre. El cierre recibe `Get`, el mismo lector que el esquema usa dentro de `afterStateUpdated`. `Get.get` resuelve un camino relativo al contenedor del componente. Un camino que empieza por `/` es absoluto.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val section = Section.make("Profile")
section.label("Title")
section.label { get -> if (get.get("/kind") == "org") "Organization" else "Title" }
section.description { get -> "About ${get.get("/kind")}" }
section.columns { 2 }
section.hidden { get -> get.get("/draft") == true }
```

</TabItem>
<TabItem label="Java">

```java
name.label(get -> "From Java");
details.columns(get -> 2);
Text.make("Hello").content(get -> "Hello");
```

</TabItem>
</Tabs>

Gana la última llamada. `label("Title")` después de un cierre guarda la cadena fija y descarta el cierre. La misma forma está en `heading`, `description`, `hidden`, `visible`, `disabled`, `columnSpan`, `columns`, `maxWidth`, `content`, `size`, `url`, `alt`, `imageHeight` e `imageWidth`.

`extraAttributes` fusiona un mapa de atributos HTML en la raíz del componente. Los layouts, los primes, las acciones, las entradas de infolist, las columnas de tabla y los campos de formulario lo tienen, porque comparten el componente de esquema (las columnas conservan los mismos métodos en la raíz de la columna). Pasa un mapa o un cierre. Un nombre que no es un nombre de atributo HTML se salta. Los valores se escapan.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
Section.make().extraAttributes(mapOf("data-section" to "intro"))
Text.make("note").extraAttributes { mapOf("data-kind" to "note") }
```

</TabItem>
<TabItem label="Java">

```java
Section.make().extraAttributes(Map.of("data-section", "intro"));
Text.make("note").extraAttributes(get -> Map.of("data-kind", "note"));
```

</TabItem>
</Tabs>

`hidden(true)` y `visible(false)` siguen tomando un booleano. `hidden { ... }` y `visible { ... }` se recalculan cuando el esquema se renderiza o cuando corre `isHidden`.

## Estado

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
schema.fill(mapOf("user.city" to "Kona"))
schema.get("user.city") // "Kona"
```

</TabItem>
<TabItem label="Java">

```java
schema.fill(Map.of("user.city", "Kona"));
schema.get("user.city"); // "Kona"
```

</TabItem>
</Tabs>

Dentro de un componente bajo `statePath("user")`:

| Llamada | Resultado |
|------|--------|
| `get("name")` | el hermano en `user.name` |
| `get("../name")` | sigue siendo `user.name` — `..` no sale del prefijo del esquema |
| `get("/user.city")` | lectura absoluta |
| `get(".")`, `get("..")`, `get("")` | `null` |

`defaultValue("Ada")` escribe ese literal durante `hydrate()` cuando el camino está vacío. `defaultUsing { get -> get.get("../name") }` escribe el resultado del cierre. Un segundo `hydrate()` deja en su sitio un valor existente.

`dehydrate()` devuelve un mapa de caminos que deben guardarse. Un componente oculto se omite salvo `dehydratedWhenHidden(true)`. `dehydrated(false)` omite el componente aunque sea visible.

`afterStateUpdated` corre después de `set` cuando el camino coincide con un componente. El hook recibe el valor nuevo, el valor antiguo, `Get` y `Set`. `set.set("slug", "bea", false)` escribe un hermano y no corre el hook de actualización de ese hermano.

## Layouts

Recurres a un layout cuando un campo tras otro no basta. Una sección, una cuadrícula, pestañas o un asistente siguen siendo un componente de esquema. La página Desk apila un formulario, un infolist y una tabla en el cuerpo, que es el layout que ves en el ejemplo.

<FireflyShot file="schema-layout.png" description="El cuerpo de la página Desk en http://127.0.0.1:4017/admin/desk, con el formulario, el infolist de nombre y la tabla de notes uno tras otro." />

| Tipo | Papel |
|------|------|
| `Grid.make(columns)` | Cuadrícula de columnas. `schema(...)` pone los hijos |
| `Flex.make()` | Fila de hijos |
| `Fieldset.make(legend)` | Grupo con una leyenda. `required(true)` lo marca |
| `Section.make(heading)` | Encabezado, descripción y slots: `afterHeader`, `beforeLabel`, `afterLabel`, `aboveContent`, `belowContent`, `footer`. `aside(true)` y `formBefore(true)` añaden atributos de datos |
| `Tabs.make()` | `tabs(...)`, `activeTab`, `vertical`, `scrollable`, `persistTabInQueryString` |
| `Tab.make(label)` | Un panel. `badge`, `badgeIcon`, `deferBadge` |
| `Wizard.make()` | `steps(...)`, `nextStep`, `previousStep`, `goToStep`. `skippable(true)` permite un salto |
| `WizardStep.make(label)` | Un paso. `icon`, `completedIcon`, `formWrapper` |
| `Callout.make(heading)` | `info()`, `success()`, `warning()`, `danger()` o `status(...)`. `color` sustituye el color del estado |
| `EmptyState.make(heading)` | Encabezado más un `footer` opcional |

`configureUsing` en un layout corre para cada `make()` posterior de esa clase. Pasa `null` para limpiarlo.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
Section.configureUsing { it.aside(true) }
```

</TabItem>
<TabItem label="Java">

```java
Section.configureUsing(section -> { section.aside(true); });
```

</TabItem>
</Tabs>

El nivel de encabezado empieza en 2. `rootHeadingLevel` cambia el inicio. Las secciones anidadas lo incrementan, y el nivel se detiene en 6.

## Primes

`Text.make(content)` renderiza un párrafo. `content`, `size`, `badge(true)` y `js()` lo cambian. `SchemaIcon.make("home")` incrusta un icono del conjunto de soporte (`home`, `bars`, `user`, `x`). `Image.make(url)` toma `alt`, `url`, `imageHeight`, `imageWidth` e `imageSize`. `UnorderedList.make("one", "two")` renderiza los elementos; `items { listOf("Kona") }` los sustituye en el momento del render.

## Actualizaciones en vivo

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
field.live()
field.liveOnBlur()
field.liveDebounce(400)
field.reactive()   // same binding as live()
field.lazy()       // same binding as liveOnBlur()
```

</TabItem>
<TabItem label="Java">

```java
field.live();
field.liveOnBlur();
field.liveDebounce(400);
field.reactive();
field.lazy();
```

</TabItem>
</Tabs>

`live()` renderiza `wire:model.live`. `liveOnBlur()` y `lazy()` renderizan `wire:model.blur`. `liveDebounce(400)` renderiza `wire:model.live.debounce.400ms`. Cada uno también pone `data-ff-entangle="@entangle(path)"`. `afterStateUpdatedJs("watch")` guarda la expresión en `data-ff-updated-js`. La página no evalúa esa cadena en el servidor.

`hiddenJs` y `visibleJs` guardan expresiones del navegador de la misma forma.

## Tu propio componente

Subclasifica `Component`. El nombre del constructor es la clave de estado.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class Banner(name: String) : Component(name)
```

</TabItem>
<TabItem label="Java">

```java
public class NameField extends Component {
    public NameField() { super("name"); }
}
```

</TabItem>
</Tabs>

`view("notes.banner")` renderiza esa vista Crema cuando está puesto `Schema.crema(engine)`. La vista recibe `path`, `content` y `label`. Sin motor, el render emite `<div data-ff-view="notes.banner">`.

`./grind make:firefly-layout Banner` escribe una clase de layout y una vista Crema bajo `app/firefly/layouts`. `--lang=java` escribe una clase Java. La vista usa `x-data="ffField"` y `@entangle`.

## Alpine

`AlpineScripts.source()` es el script que registra `ffField`, `ffEntry`, `ffColumn` y `ffAction`. Esas fábricas entrelazan el estado con `$wire.$entangle` y llaman a acciones del servidor con `$wire.$call`.

## Esquemas diferidos

`deferLoading(true)` hace que `render()` devuelva un marcador de carga hasta `loadDeferred()`. El esquema necesita `key(...)`. Un esquema diferido sin clave lanza `FireflyException` (`Deferred schema is missing a key`).

## Lo que este módulo no hace

No abre diálogos, no registra rutas ni renderiza entradas como un select o un selector de fecha. Los botones y los diálogos de confirmación se construyen con [Acciones](/docs/firefly/actions/). Este módulo es el árbol y el estado sobre los que se sientan esas piezas.
