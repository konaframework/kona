El **enrutador** decide qué código corre para una petición HTTP entrante. Una **ruta** es una entrada: un conjunto de métodos HTTP, un patrón de ruta como `/users/{id}`, middleware opcional, un nombre opcional y un **manejador** — una función con forma `Request → Response`.

Cuando llega una petición, el [kernel HTTP](../kernel-server/) pide al enrutador que **resuelva** método + ruta. Si hay coincidencia, el kernel copia los parámetros de ruta a la petición, ejecuta el pipeline de middleware de esa ruta y luego el manejador. Si falla, el enrutador (y después el manejador de excepciones) produce respuestas **404** o **405**.

Esta guía cubre toda la superficie pública de enrutamiento que se publica hoy: APIs de registro, parámetros, recursos, grupos, URLs con nombre, redirecciones desde manejadores, el comportamiento de HEAD/OPTIONS, ayudantes de inspección y cómo probar rutas. Los controladores, las pilas de middleware global y los ayudantes de URL absoluta o firmada tienen sus propias páginas; esta página enlaza en lugar de duplicarlos.

:::tip[Dónde viven las rutas]
Las aplicaciones de `kona new` registran las rutas después de `boot()` en dos clases: `WebRoutes` (navegador / HTML) y `ApiRoutes` (JSON bajo `/api`). Mantén los manejadores finos; pon la validación y la forma de la respuesta en los [controladores](../controllers/).
:::

## Qué ocurre en una petición

1. El transporte (Netty) construye un `Request` con el método HTTP real y la ruta normalizada.
2. El middleware global (sesión, CSRF y demás — consulta [Middleware](../middleware/)) corre alrededor del resto del pipeline.
3. `Router.resolve(method, path)` encuentra la primera ruta que coincide, o lanza `NotFoundException` / `MethodNotAllowedException`, o sintetiza una respuesta `OPTIONS` automática.
4. Los valores `{param}` capturados se guardan en la petición bajo `param` y `route.param`.
5. Corre el middleware de ruta (primero el del grupo, luego `.middleware(...)` de la ruta) y después el manejador.
6. En `HEAD`, el kernel vacía el cuerpo de la respuesta cuando el manejador vuelve (el estado y las cabeceras se quedan).

Registra todas las rutas **antes** de que el servidor acepte tráfico. El singleton `Router` compartido no está pensado para mutarse mientras sirve peticiones.

## Obtener el enrutador

`HttpServiceProvider` registra un `Router` compartido en el contenedor de la aplicación. Resuélvelo después de que la aplicación haya arrancado: en el método `boot` de un proveedor, o justo después de `boot()` en el bootstrap:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val app = Kona.create(args)
    .providers(HttpServiceProvider(), /* … */, AppServiceProvider())
    .boot()
WebRoutes().register(app.resolve(Router::class.java))
ApiRoutes().register(app.resolve(Router::class.java))
```

</TabItem>
<TabItem label="Java">

```java
Application app = Kona.create(args)
    .providers(new HttpServiceProvider(), /* … */, new AppServiceProvider())
    .boot();
new WebRoutes().register(app.resolve(Router.class));
new ApiRoutes().register(app.resolve(Router.class));
```

</TabItem>
</Tabs>

La misma instancia de `Router` respalda la [generación de URL](../url-generation/) (`UrlGenerator` / `Url.route` / `route(...)` de nivel superior).

## La ruta más simple

Un manejador es cualquier `Handler` (`Request → Response`). En Kotlin suele ser una lambda final; en Java una lambda o una referencia a método:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/") { Response.text("home") }
router.post("/echo") { request -> Response.json(request.all()) }
```

</TabItem>
<TabItem label="Java">

```java
router.get("/", request -> Response.text("home"));
router.post("/echo", request -> Response.json(request.all()));
```

</TabItem>
</Tabs>

## Llamar a un controlador {#call-a-controller}

La mayoría de las rutas de producción apuntan a un método de **controlador** en lugar de una lambda en línea. Un controlador es una clase normal con métodos que reciben un `Request` y devuelven un `Response`. **No** tienes que extender `Controller` salvo que quieras los ayudantes compartidos de `validate`. Consulta [Controladores](../controllers/).

El andamiaje predeterminado cablea una página de bienvenida así:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
package routes

import app.http.controllers.WelcomeController
import org.konaframework.http.Router

class WebRoutes {
    fun register(router: Router) {
        val welcome = WelcomeController()
        router.get("/") { welcome.index(it) }.name("welcome")
    }
}
```

</TabItem>
<TabItem label="Java">

```java
package routes;

import app.http.controllers.WelcomeController;
import org.konaframework.http.Router;

public final class WebRoutes {
    public void register(Router router) {
        WelcomeController welcome = new WelcomeController();
        router.get("/", welcome::index).name("welcome");
    }
}
```

</TabItem>
</Tabs>

Lo que importa en este estilo:

1. **Instancia** el controlador (pasa `Application` cuando el controlador necesita el contenedor o la configuración).
2. **Enlaza** un método que acepta `Request` y devuelve `Response` — Kotlin `{ welcome.index(it) }`, Java `welcome::index` — para que el IDE autocomplete y compruebe el tipo de la acción.
3. Opcionalmente **nombra** la ruta con `.name("…")` para poder construir URLs después.

Genera un esqueleto con [`./grind make:controller Post`](../../grind/commands/#grind-makecontroller) (`--resource` escribe una subclase de `BaseResourceController`). Pon la validación y la forma de la respuesta en el controlador; deja los archivos de rutas como el mapa de URL → acción.

## Declarar rutas (verbos HTTP)

Hay un método de registro por cada método HTTP habitual, más dos formas generales:

| Método | Coincide con |
|--------|---------|
| `get(uri, handler)` | `GET` (y `HEAD` por fallback — consulta [HEAD, OPTIONS, 404 y 405](#head-options-404-and-405)) |
| `post(uri, handler)` | `POST` |
| `put(uri, handler)` | `PUT` |
| `patch(uri, handler)` | `PATCH` |
| `delete(uri, handler)` | `DELETE` |
| `options(uri, handler)` | `OPTIONS` (sustituye el comportamiento automático de OPTIONS para esa ruta) |
| `any(uri, handler)` | Todos los `Router.VERBS`: `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS` |
| `match(methods, uri, handler)` | Cada método de `methods` (sin distinguir mayúsculas; se guarda en mayúsculas, se quitan duplicados) |

Cada llamada devuelve la `Route` nueva, así que puedes encadenar `.name(...)` y `.middleware(...)`.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/") { Response.text("home") }.name("home")
router.post("/users") { users.store(it) }
router.put("/users/{id}") { users.update(it) }
router.patch("/users/{id}") { users.patch(it) }
router.delete("/users/{id}") { users.destroy(it) }
router.options("/users") { Response.noContent().header("Allow", "GET,POST,OPTIONS") }
router.match(listOf("PUT", "PATCH"), "/profile") { profile.update(it) }
router.any("/health") { Response.text("ok") }
```

</TabItem>
<TabItem label="Java">

```java
router.get("/", request -> Response.text("home")).name("home");
router.post("/users", users::store);
router.put("/users/{id}", users::update);
router.patch("/users/{id}", users::patch);
router.delete("/users/{id}", users::destroy);
router.options("/users", request -> Response.noContent().header("Allow", "GET,POST,OPTIONS"));
router.match(List.of("PUT", "PATCH"), "/profile", profile::update);
router.any("/health", request -> Response.text("ok"));
```

</TabItem>
</Tabs>

`Router.VERBS` es una lista pública (`@JvmField`) de los siete métodos que registra `any`. Úsala cuando necesites el mismo conjunto.

### Rutas y orden de coincidencia

- Las barras iniciales y finales de la ruta **registrada** se normalizan al unir prefijos: `"users"`, `"/users"` y `"/users/"` se vuelven `/users`.
- Las rutas entrantes se normalizan con `HttpPaths.normalize`: las `/` repetidas se colapsan, se asegura una `/` inicial y se quita una `/` final (salvo en `/` mismo). Así `/users/`, `//users` y `/users` coinciden con el mismo `/users` registrado.
- El texto estático debe coincidir exactamente y **distingue mayúsculas**.
- Las rutas se comprueban **en el orden de registro**; gana la **primera** coincidencia. Registra las rutas específicas antes que las generales: `/users/me` debe ir antes de `/users/{id}`, o `me` se capturará como un id.
- Una ruta debe declarar al menos un método HTTP; construir una lista de métodos vacía lanza `IllegalArgumentException`.

## Parámetros de ruta {#path-parameters}

Un segmento escrito como `{name}` captura **un segmento de ruta** (cualquier cosa hasta la siguiente `/`). Los nombres de parámetro deben empezar por una letra o un guion bajo y pueden contener letras, dígitos y guiones bajos (`[a-zA-Z_][a-zA-Z0-9_]*`).

Los valores capturados se decodifican (`/files/a%20b` → `a b`). Un `+` literal en la ruta se queda como `+` (no se trata como espacio). Si un valor no se puede decodificar, se usa el texto en crudo. Los valores que al decodificarse incluyen `/` (por ejemplo `%2F`) se vuelven un solo valor de parámetro que contiene `/`: siguen viniendo de un segmento de la ruta de la petición.

En el enrutador actual **no** hay parámetros opcionales (`{id?}`), **no** hay restricciones regex por parámetro y **no** hay comodines catch-all `{path}`. Registra una segunda ruta cuando un segmento es opcional, y comprueba los formatos dentro del manejador o con [validación](../validation/).

### Leer parámetros

Tras una coincidencia, el kernel guarda cada valor en la petición en dos sitios:

| Clave | Ejemplo |
|-----|---------|
| `name` | `request.route("id")` o `request.getAttribute("id")` |
| `route.name` | `request.getAttribute("route.id")` |

Prefiere `request.route(key)`: devuelve un `String?` (o un valor predeterminado) y convierte el atributo a cadena. Más ayudantes de petición: [Petición y respuesta](../request-response/#route-parameters-requestroute).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/users/{id}/posts/{slug}") { request ->
    val id = request.route("id")!!.toLong()
    val slug = request.route("slug")!!
    Response.json(mapOf("user" to id, "post" to slug))
}
```

</TabItem>
<TabItem label="Java">

```java
router.get("/users/{id}/posts/{slug}", request -> {
    long id = Long.parseLong(request.route("id"));
    String slug = request.route("slug");
    return Response.json(Map.of("user", id, "post", slug));
});
```

</TabItem>
</Tabs>

Los valores son siempre cadenas de la ruta: conviértelos tú (`toLong()`, `UUID.fromString`, y así). Las claves ausentes devuelven `null` desde `route(key)` (o el valor predeterminado que pases).

## Rutas de recurso {#resource-routes}

Un **recurso** es una colección de registros expuesta sobre un conjunto convencional de URLs. `resource(name, controller)` registra el conjunto completo (incluidas las rutas de formulario HTML) contra un `ResourceController`:

| Método(s) | Ruta | Método del controlador | Nombre de ruta |
|-----------|------|-------------------|------------|
| `GET` | `/posts` | `index` | `posts.index` |
| `GET` | `/posts/create` | `create` | `posts.create` |
| `POST` | `/posts` | `store` | `posts.store` |
| `GET` | `/posts/{id}` | `show` | `posts.show` |
| `GET` | `/posts/{id}/edit` | `edit` | `posts.edit` |
| `PUT`, `PATCH` | `/posts/{id}` | `update` | `posts.update` |
| `DELETE` | `/posts/{id}` | `destroy` | `posts.destroy` |

El orden de registro coincide con la tabla: `create` se registra **antes** de `show`, así que `/posts/create` nunca se captura como `{id}=create`.

### Rutas de recurso de API {#api-resource-routes}

`apiResource(name, controller)` registra el mismo mapa **sin** `create` / `edit`, la forma habitual de las API JSON:

| Método(s) | Ruta | Método del controlador | Nombre de ruta |
|-----------|------|-------------------|------------|
| `GET` | `/posts` | `index` | `posts.index` |
| `POST` | `/posts` | `store` | `posts.store` |
| `GET` | `/posts/{id}` | `show` | `posts.show` |
| `PUT`, `PATCH` | `/posts/{id}` | `update` | `posts.update` |
| `DELETE` | `/posts/{id}` | `destroy` | `posts.destroy` |

:::caution[Recurso de API y `/resource/create`]
Como `apiResource` no registra `create`, una petición a `GET /posts/create` coincide con `show` y `id` igual a `"create"`. Usa `resource(...)` cuando necesites URLs HTML de crear/editar, o reserva esa ruta tú mismo antes del registro del recurso.
:::

### Filtrar acciones: `only` y `except`

Tanto `resource` como `apiResource` aceptan colecciones opcionales `only` / `except` de nombres de acción (`index`, `create`, `store`, `show`, `edit`, `update`, `destroy`). Los nombres se comparan sin distinguir mayúsculas.

- **`only`**: conserva solo esas acciones.
- **`except`**: descarta esas acciones.
- Si ambos están definidos, se aplica primero `only` y luego `except`.

Pasa una **instancia** de tu `ResourceController` (constrúyela tú, o resuélvela del contenedor y pasa la instancia). Las rutas y los nombres respetan el grupo que las rodea, así que dentro de un grupo con prefijo `/api` y nombre `api.` obtienes `/api/posts` y `api.posts.index`. Pasa el nombre del recurso **sin** barra inicial.

Implementa cada acción tú mismo, o extiende `BaseResourceController` y anula solo las que necesites: las acciones no implementadas lanzan `NotFoundException` (HTTP 404). Detalles: [Controladores → Controladores de recurso](../controllers/#resource-controllers).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class PostController : BaseResourceController() {
    override fun index(request: Request) = Response.json(posts.all())
    override fun show(request: Request) =
        Response.json(posts.find(request.route("id")!!))
    override fun store(request: Request) =
        Response.json(posts.create(request.data()), 201)
    override fun update(request: Request) =
        Response.json(posts.update(request.route("id")!!, request.data()))
    override fun destroy(request: Request): Response {
        posts.delete(request.route("id")!!)
        return Response.noContent()
    }
}

router.resource("posts", PostController())
router.apiResource("posts", PostController())
router.apiResource("notes", NotesController(), only = listOf("index", "show"))
router.apiResource("things", ThingsController(), except = listOf("destroy"))
```

</TabItem>
<TabItem label="Java">

```java
public class PostController extends BaseResourceController {
    @Override public Response index(Request request) { return Response.json(posts.all()); }
    @Override public Response show(Request request) {
        return Response.json(posts.find(request.route("id")));
    }
    @Override public Response store(Request request) {
        return Response.json(posts.create(request.data()), 201);
    }
    @Override public Response update(Request request) {
        return Response.json(posts.update(request.route("id"), request.data()));
    }
    @Override public Response destroy(Request request) {
        posts.delete(request.route("id"));
        return Response.noContent();
    }
}

router.resource("posts", new PostController());
router.apiResource("posts", new PostController());
// only, except — pass null for the filter you do not use
router.apiResource("notes", new NotesController(), List.of("index", "show"), null);
router.apiResource("things", new ThingsController(), null, List.of("destroy"));
```

</TabItem>
</Tabs>

Cuando omites una acción con `only` / `except`, la ruta puede seguir existiendo bajo otro método. Ejemplo: `resource(..., only = listOf("index", "show"))` sigue registrando `GET /items`, así que `POST /items` devuelve **405** (método no permitido), no 404.

Empareja los payloads JSON con [Recursos de API](../api-resources/).

## Grupos

Un **grupo** aplica ajustes compartidos a cada ruta declarada dentro:

- **prefix**: se antepone a cada ruta (`/api` + `/me` → `/api/me`),
- **name**: se antepone a cada nombre de ruta (`api.` + `me` → `api.me`),
- **middleware**: corre antes del middleware propio de cada ruta.

El `ApiRoutes` del andamiaje es un grupo típico:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.group(prefix = "/api", name = "api.") {
    get("/health") { Response.json(mapOf("status" to "ok")) }.name("health")
    // Full path /api/health, name api.health

    apiResource("pings", PingApiController())
    // /api/pings, names api.pings.index, …
}
```

</TabItem>
<TabItem label="Java">

```java
router.prefix("/api").name("api.").group(api -> {
    api.get("/health", request -> Response.json(Map.of("status", "ok"))).name("health");
    api.apiResource("pings", new PingApiController());
});
```

</TabItem>
</Tabs>

### Grupos anidados y middleware

Los grupos interiores se suman a los exteriores: los prefijos se unen con `/`, los prefijos de nombre se concatenan y las listas de middleware se añaden (el exterior primero). Los ajustes del grupo se capturan cuando se registra cada ruta, y terminan cuando vuelve el bloque del grupo, aunque el bloque lance (se restaura la pila anterior de prefijo / nombre / middleware).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.group(prefix = "/api", name = "api.", middleware = listOf(Authenticate())) {
    get("/me") { Response.json(mapOf("user" to it.getAttribute("user"))) }.name("me")

    group(prefix = "/admin", name = "admin.", middleware = listOf(RequireAdmin())) {
        get("/stats") { Response.json(stats()) }.name("stats")
        // /api/admin/stats, name api.admin.stats
    }
}
```

`router.routes { … }` es un ayudante pequeño que ejecuta un bloque con el enrutador como `this`, útil para mantener ordenados los archivos de rutas.

</TabItem>
<TabItem label="Java">

```java
router.prefix("/api").name("api.").middleware(new Authenticate()).group(api -> {
    api.get("/me", request -> Response.json(Map.of("user", request.getAttribute("user")))).name("me");

    api.prefix("/admin").name("admin.").middleware(new RequireAdmin()).group(admin ->
        admin.get("/stats", request -> Response.json(stats())).name("stats"));
});
```

O pasa los ajustes en posición:

```java
router.group("/v1", v1 -> v1.get("/ping", request -> Response.text("pong")));
router.group("/v2", List.of(new Authenticate()), v2 -> { /* ... */ });
router.group("/v3", "v3.", List.of(new Authenticate()), v3 -> { /* ... */ });
```

`middleware(...)` en el builder fluido acepta varios argumentos de middleware o una `List`.

</TabItem>
</Tabs>

## Middleware en una ruta {#middleware-on-a-route}

Adjunta middleware a una ruta con `.middleware(...)`. El middleware de ruta corre **después** de cualquier middleware de grupo de esa ruta. Las pilas globales (sesión, CSRF y demás) se configuran en `bootstrap.Middleware` y se aplican al kernel: envuelven el enrutamiento por completo, así que siguen viendo las respuestas 404/405. Consulta [Middleware](../middleware/).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.post("/webhooks/stripe") { stripe.handle(it) }
    .middleware(VerifyStripeSignature())
```

</TabItem>
<TabItem label="Java">

```java
router.post("/webhooks/stripe", stripe::handle)
    .middleware(new VerifyStripeSignature());
```

</TabItem>
</Tabs>

## Rutas con nombre y generación de URL {#named-routes-and-url-generation}

`.name("…")` da un nombre a una ruta para que puedas construir su URL después sin fijar el camino en el código. Los prefijos de nombre del grupo se aplican solos (`api.` + `health` → `api.health`). Las acciones de recurso se nombran como `{resource}.{action}`.

### Ruta desde el enrutador

`router.route(name, params)` devuelve el **camino** con cada `{key}` sustituido por el valor correspondiente:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/users/{id}") { users.show(it) }.name("users.show")

val path = router.route("users.show", mapOf("id" to "42"))   // "/users/42"
```

</TabItem>
<TabItem label="Java">

```java
router.get("/users/{id}", users::show).name("users.show");

String path = router.route("users.show", Map.of("id", "42"));  // "/users/42"
```

</TabItem>
</Tabs>

Reglas:

- Los valores se insertan tal cual: **no** se codifican. Codifícalos antes si pueden contener `/`, espacios u otros caracteres reservados.
- Los marcadores sin valor se quedan en la salida como `{key}`.
- Un nombre desconocido lanza `IllegalArgumentException("Route [name] not defined")`.
- Si dos rutas comparten un nombre, se usa la **primera** registrada.

### URLs absolutas y ayudantes

Con `HttpServiceProvider` arrancado, prefiere:

| Ayudante | Resultado |
|--------|--------|
| `Url.route(name, params)` / `route(name, params)` de nivel superior en Kotlin | URL absoluta o enraizada vía `UrlGenerator` (raíz `app.url`) |
| `Url.to(path)` / `url(path)` | Une un camino a la raíz configurada |
| `UrlGenerator.signedRoute(...)` | Ruta con nombre firmada — consulta [Generación de URL](../url-generation/) |

```kotlin
Response.redirect(route("users.show", mapOf("id" to "42")))
```

## Redirecciones desde manejadores

El enrutador **no** tiene un ayudante de registro `redirect(...)`. Redirige devolviendo una respuesta de redirección desde el manejador (o el controlador):

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/home") { Response.redirect("/") }                    // 302 + Location
router.get("/old") { Response.redirect("/new", 301) }
router.post("/login") { request ->
    // … authenticate …
    Response.redirect(route("dashboard"))
}
router.get("/back") { request -> Response.back(request) }         // previous / Referer / "/"
```

</TabItem>
<TabItem label="Java">

```java
router.get("/home", request -> Response.redirect("/"));
router.get("/old", request -> Response.redirect("/new", 301));
router.post("/login", request -> Response.redirect(Url.route("dashboard")));
router.get("/back", request -> Response.back(request));
```

</TabItem>
</Tabs>

`Response.back(request, fallback, status)` usa `_previous.url` de la sesión, luego la cabecera `Referer`, y luego `fallback` (predeterminado `/`). Los ayudantes de flash (`with`, `withInput`, `withErrors`) van con el middleware de sesión. Consulta [Petición y respuesta](../request-response/).


</TabItem>
<TabItem label="Java">


</TabItem>

## HEAD, OPTIONS, 404 y 405 {#head-options-404-and-405}

Estas reglas salen de `Router.find` / `Router.resolve` y del kernel HTTP:

| Petición | Qué ocurre |
|---------|--------------|
| `HEAD /path`, y solo está registrado `GET` | Corre la ruta `GET` (incluido su middleware). El kernel vacía después el cuerpo; se conservan el estado y las cabeceras. Una ruta `HEAD` explícita (vía `match` o `any`), si se registró primero, gana. |
| `OPTIONS /path`, ninguna ruta acepta `OPTIONS`, pero la ruta existe bajo otros métodos | `200` automático con cuerpo vacío y una cabecera `Allow` que lista los métodos registrados para esa ruta, en orden de registro, separados por comas **sin espacios** (por ejemplo `GET,HEAD,POST`). El middleware de ruta **no** corre. |
| `options(uri, handler)` explícito para esa ruta | Corre tu manejador (la primera coincidencia sigue ganando entre las rutas OPTIONS). |
| La ruta existe, el método no está registrado | `MethodNotAllowedException` → **405** con una cabecera `Allow` (métodos unidos con `", "` — fíjate en los espacios) y un sobre JSON o HTML del manejador de excepciones. |
| Ninguna ruta coincide con el camino | `NotFoundException` → **404**. El mensaje de resolve se parece a `The route users/99 could not be found.` |

Cualquier registro `GET` implica `HEAD` en la lista `Allow` de `allowedMethods` / 405 / OPTIONS automático.

El middleware global sigue envolviendo las respuestas 404 y 405; el middleware de **ruta** nunca corre cuando no se seleccionó ninguna ruta. Consulta [Excepciones](../exceptions/) para la forma del sobre (`Accept: text/html` puede renderizar una página HTML pequeña en lugar de JSON).

## Inspeccionar y resolver rutas

| API | Comportamiento |
|-----|----------|
| `router.all()` | Lista instantánea de cada `Route` registrada |
| `router.find(method, path)` | El primer `MatchResult` (ruta + mapa de parámetros), o `null`; HEAD cae a GET; **no** lanza |
| `router.resolve(method, path)` | Como `find`, pero lanza 404/405 o devuelve la coincidencia OPTIONS sintética |
| `router.allowedMethods(path)` | Métodos registrados para esa ruta (`GET` implica `HEAD` en la lista) |
| `router.route(name, params)` | Construye un camino a partir de una ruta con nombre |

Cada `Route` expone `methods`, `method` (el primero declarado), `uri`, `name`, `middleware`, más `match` / `matchPath` / `uriFor` para uso avanzado. `MatchResult` es una data class: `route` + `parameters`. Los comandos de grind de abajo leen esta misma lista.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.all().forEach { route ->
    println("${route.methods} ${route.uri} ${route.name ?: ""}")
}

val match = router.find("GET", "/users/42")
if (match != null) {
    println(match.parameters["id"]) // "42"
}
```

</TabItem>
<TabItem label="Java">

```java
for (Route route : router.all()) {
    System.out.println(route.getMethods() + " " + route.getUri() + " " + route.getName());
}

MatchResult match = router.find("GET", "/users/42");
if (match != null) {
    System.out.println(match.getParameters().get("id")); // "42"
}
```

</TabItem>
</Tabs>

## Listar rutas con grind {#listing-routes-with-grind}

Desde un directorio de aplicación (después de `./gradlew classes`):

```bash
./grind route:list
./grind route:list --json
./grind route:list --method=GET --name=users
./grind route:list --path=/api --except-path=/api/internal
./grind route:cache
./grind route:clear
```

`route:list` arranca tu app in-process e imprime el `Router` vivo como una tabla: **Method**, **URI**, **Name**, **Action**, **Middleware**. Las lambdas aparecen como `Closure`; las clases `Handler` con nombre muestran su nombre cualificado. Las rutas `GET` se listan como `GET` (HEAD sigue coincidiendo en tiempo de ejecución — consulta la tabla de arriba). Las rutas de varios métodos, como el `update` de un recurso, imprimen `PUT|PATCH`.

Filtros útiles: `--method=`, `--name=`, `--path=`, `--except-path=`, `--except-vendor`, `--only-vendor`, `--compact`, `--columns=`, `--sort=`, `--reverse`, `--json`. Referencia completa de flags: [Comandos integrados — route:list](../../grind/commands/#grind-routelist).

`route:cache` escribe `bootstrap/cache/routes.json` (una instantánea de esa tabla). El kernel HTTP no carga el archivo; el registro de rutas compilado ya corre en cada arranque. `route:clear` borra la instantánea.

Si grind no encuentra un proyecto Gradle, o la app arrancada no tiene un `Router` en el contenedor, el comando sale con `1`. Cero rutas coincidentes sigue siendo salida `0` (un aviso, o `[]` con `--json`).

## Casos de uso habituales

### Separar las tablas web y de API

Deja las rutas de navegador y las de JSON en clases distintas, y comparte un `Router`:

```kotlin
WebRoutes().register(router)
ApiRoutes().register(router) // typically group(prefix = "/api", name = "api.") { … }
```

### Prefijo de API versionada

```kotlin
router.group(prefix = "/api/v1", name = "api.v1.") {
    apiResource("orders", OrderApiController())
}
```

### Proteger un subconjunto de rutas

```kotlin
router.group(middleware = listOf(Authenticate())) {
    get("/settings") { settings.edit(it) }.name("settings.edit")
    post("/settings") { settings.update(it) }.name("settings.update")
}
```

### Segmento opcional con dos rutas

```kotlin
router.get("/docs") { docs.index(it) }.name("docs.index")
router.get("/docs/{page}") { docs.show(it) }.name("docs.show")
```

### Redirigir URLs antiguas

```kotlin
router.get("/blog/{slug}") { request ->
    Response.redirect(route("posts.show", mapOf("id" to request.route("slug")!!)), 301)
}
```

## Referencia de API (tipos de enrutamiento)

### `Router`

| Miembro | Papel |
|--------|------|
| `get` / `post` / `put` / `patch` / `delete` / `options` | Registra un método |
| `any` / `match` | Registra varios métodos |
| `resource` / `apiResource` | Mapas CRUD convencionales (`only` / `except` opcionales) |
| `group(...)` | DSL de Kotlin o sobrecargas `Consumer` de Java |
| `prefix` / `name` / `middleware` | Empieza un `RouteGroup` fluido de Java |
| `routes { }` | Bloque de Kotlin con el enrutador como receptor |
| `all` / `find` / `resolve` / `allowedMethods` / `route` | Inspección y caminos con nombre |
| `VERBS` | `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS` |

### `Route`

| Miembro | Papel |
|--------|------|
| `methods` / `method` | Verbos declarados / primer verbo |
| `uri` | Patrón de ruta completo (después del prefijo de grupo) |
| `name` / `name(value)` | Nombre opcional (el espacio de nombres del grupo se aplica en `name(...)`) |
| `middleware` / `middleware(...)` | Lista de middleware de grupo + ruta |
| `action` | `Handler` |
| `match` / `matchPath` / `uriFor` | Coincidencia y construcción de ruta |

### `RouteGroup` (fluido de Java)

Encadena `prefix`, `name`, `middleware` (vararg o `List`) y luego `group(Consumer)`.

### `MatchResult`

`route: Route`, `parameters: Map<String, String>` (ordenado por aparición en el patrón).

### `ResourceController` / `BaseResourceController`

Siete acciones: `index`, `create`, `store`, `show`, `edit`, `update`, `destroy`. `BaseResourceController` lanza `NotFoundException` para cualquier acción que no anules.

### `Handler` / `InvokableController`

`Handler.handle(Request): Response`. `InvokableController.invoke` se adapta vía `asHandler()` / `Controllers.asHandler`.

## Trampas y preguntas

**¿Por qué `/users/me` cae en `{id}`?**  
El orden de registro. Pon los segmentos estáticos antes que los parametrizados.

**¿Por qué `POST /items` es un 405 después de `only = listOf("index", "show")`?**  
La ruta sigue coincidiendo con una ruta `GET` registrada, así que el enrutador informa de método no permitido en lugar de no encontrado.

**¿Por qué `GET /api/posts/create` llama a `show`?**  
`apiResource` no tiene acción `create`. Usa el `resource` completo o registra una ruta explícita primero.

**¿Los formularios HTML suplantan PUT/PATCH/DELETE?**  
La directiva `@method` de Crema emite un campo oculto `_method` para las plantillas, pero el kernel HTTP y el enrutador coinciden hoy con el método **real** de la petición. Los clientes que no pueden enviar `PUT`/`PATCH`/`DELETE` necesitan un método real (o una ruta `POST` dedicada). Consulta [Formularios de Crema](../../crema/forms/#method-spoofing).

**¿Hay rutas fallback / catch-all?**  
No como una API dedicada. Registra al final una ruta parametrizada amplia si necesitas un manejador de página 404 propio, o personaliza el [manejador de excepciones](../exceptions/).

**¿Puedo limitar `{id}` a dígitos?**  
No en el enrutador. Valida en el manejador o con reglas de [validación](../validation/).

**¿Debo mutar el enrutador en tiempo de ejecución?**  
No. Registra durante el arranque y luego sirve.

## Qué no está en el enrutador (hoy)

Documentado aquí para que no busques APIs que faltan:

- Parámetros de ruta opcionales y restricciones regex/where
- Enrutamiento por dominio / subdominio
- Ayudantes de registro `fallback()` / catch-all
- Macros de ruta `redirect()` / `view()` (usa respuestas del manejador)
- Sustitución automática de `_method` en posts de formulario (Crema puede emitir el campo; el enrutamiento lo ignora — [Formularios de Crema](../../crema/forms/#method-spoofing))
