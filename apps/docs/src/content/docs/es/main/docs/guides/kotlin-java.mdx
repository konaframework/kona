import { Tabs, TabItem } from '@astrojs/starlight/components';

Kona está escrito en Kotlin, pero las aplicaciones Java son un objetivo de primera clase. Cada API pública está formada para que un sitio de llamada Java se lea con naturalidad, y el repositorio de Kona mantiene un ejemplo Java (`samples/hello-java`) junto al de Kotlin (`samples/hello-kotlin`) como parte de sus pruebas de regresión. Cuando una página de estos docs muestra ambos lenguajes, **el comportamiento es idéntico**; solo difiere la sintaxis.

Esta página explica las convenciones detrás de eso, para que puedas predecir cómo se ve cualquier API de Kona desde tu lenguaje sin buscar un ejemplo.

## Cómo aparecen las APIs de Kotlin en Java

Kotlin compila a clases JVM ordinarias. Unas cuantas características del lenguaje se traducen de formas predecibles:

| Declaración Kotlin | Lo que escribe el código Kotlin | Lo que escribe el código Java |
|--------------------|-------------------------|-----------------------|
| Propiedad `val container` | `app.container` | `app.getContainer()` |
| Propiedad mutable `var status` | `response.status = 201` | `response.setStatus(201)` |
| `object Kona` con miembros `@JvmStatic` | `Kona.create(args)` | `Kona.create(args)` |
| Clase anidada `Application.Builder` | `Application.Builder` | `Application.Builder` |
| `fun interface Handler` | lambda final `{ request -> ... }` | lambda `request -> ...` o method reference |
| Tipo de función `(Container) -> T` | `{ c -> Greeter() }` | `c -> new Greeter()` |
| Tipo de retorno `T?` (nullable) | el compilador obliga a una comprobación de null | puede devolver `null`; compruébalo tú |

Kona marca sus puntos de entrada (`Kona`, `Env`, `Application.builder`, `Response.text`/`json`/`html`, `Request.get`/`post`, `Config.toBoolean`) con `@JvmStatic`, así que Java los llama como métodos estáticos planos sin un salto `.INSTANCE` o `.Companion`.

## Arrancar una aplicación

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val app: Application = Kona.create(args)
    .providers(HttpServiceProvider(), AppServiceProvider())
    .configure { config -> config.set("app.name", "Demo") }
    .boot()
```

</TabItem>
<TabItem label="Java">

```java
Application app = Kona.create(args)
    .providers(new HttpServiceProvider(), new AppServiceProvider())
    .configure(config -> config.set("app.name", "Demo"))
    .boot();
```

</TabItem>
</Tabs>


`configure` acepta un `java.util.function.Consumer<Config>`, así que toma una lambda Java directamente y una lambda Kotlin mediante conversión SAM.

## Escribir un proveedor de servicios

`ServiceProvider` es una interfaz con `register(Application)` y `boot(Application)`. En Kotlin, `boot` tiene un cuerpo predeterminado vacío, así que un proveedor Kotlin puede omitirlo. **Los proveedores Java deben implementar ambos métodos**: el predeterminado de Kotlin no se compila como un método `default` de Java, así que deja `boot` vacío cuando no tienes nada que hacer en el arranque.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class AppServiceProvider : ServiceProvider {
    override fun register(app: Application) {
        app.container.singleton(Clock::class.java) { SystemClock() }
    }

    override fun boot(app: Application) {
        val router = app.resolve(Router::class.java)
        router.get("/time") { Response.text(app.resolve(Clock::class.java).now().toString()) }
    }
}
```

</TabItem>
<TabItem label="Java">

```java
public final class AppServiceProvider implements ServiceProvider {
    @Override
    public void register(Application app) {
        app.getContainer().singleton(Clock.class, c -> new SystemClock());
    }

    @Override
    public void boot(Application app) {
        Router router = app.resolve(Router.class);
        router.get("/time", request -> Response.text(app.resolve(Clock.class).now().toString()));
    }
}
```

</TabItem>
</Tabs>


Los tipos siempre se pasan como objetos `Class`: `Clock::class.java` en Kotlin, `Clock.class` en Java. No hay atajos de genéricos reificados, así que la misma llamada al contenedor funciona igual en ambos lenguajes.

## Manejadores

Un **manejador** es cualquier cosa que convierte un `Request` en un `Response`. `Handler` es una interfaz de un solo método, `handle(Request): Response`, así que encaja cualquier lambda o method reference con esa forma.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.get("/ping") { request -> Response.text("pong") }

val users = UserController()
router.get("/users") { users.index(it) }
```

</TabItem>
<TabItem label="Java">

```java
router.get("/ping", request -> Response.text("pong"));

UserController users = new UserController();
router.get("/users", users::index);
```

</TabItem>
</Tabs>


## Middleware y `next`

El **middleware** es una función `handle(request, next)` que corre antes de un manejador. Llamar a `next` pasa la petición más abajo en la cadena; devolver sin llamarlo termina la petición pronto con tu propia respuesta.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
import org.konaframework.http.invoke   // enables next(request)

val requireToken = Middleware { request, next ->
    if (request.header("X-Token") == "secret") next(request)
    else Response.json(mapOf("error" to "unauthorized"), 401)
}
```

</TabItem>
<TabItem label="Java">

```java
Middleware requireToken = (request, next) ->
    "secret".equals(request.header("X-Token"))
        ? next.handle(request)
        : Response.json(Map.of("error", "unauthorized"), 401);
```

</TabItem>
</Tabs>


En Kotlin, `next(request)` es una extensión de operador declarada en `org.konaframework.http`; debes importar `org.konaframework.http.invoke` para que compile. `next.handle(request)` funciona en ambos lenguajes sin ningún import.

## Grupos de rutas

Un **grupo de rutas** aplica un prefijo de URL, un prefijo de nombre de ruta y middleware a cada ruta declarada dentro. Esta es la única API con formas realmente distintas por lenguaje.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
router.group(prefix = "/api", name = "api.", middleware = listOf(requireToken)) {
    get("/me") { Response.json(mapOf("ok" to true)) }.name("me")   // GET /api/me, name "api.me"
}

// Or declare several routes with a receiver block:
router.routes {
    get("/") { Response.text("home") }
    post("/contact") { Response.noContent() }
}
```

</TabItem>
<TabItem label="Java">

```java
router.prefix("/api").name("api.").middleware(requireToken).group(api -> {
    api.get("/me", request -> Response.json(Map.of("ok", true))).name("me");
});

// Positional overloads, if you prefer:
router.group("/api", List.of(requireToken), api -> { /* ... */ });
router.group("/api", "api.", List.of(requireToken), api -> { /* ... */ });
```

</TabItem>
</Tabs>


La forma Kotlin `group(prefix =, name =, middleware =) { }` usa argumentos con nombre y una lambda receptora, así que está oculta para Java. Java obtiene la cadena fluida `prefix(...).name(...).middleware(...).group(Consumer<Router>)` y sobrecargas `Consumer`. Ambas construyen exactamente las mismas rutas.

## Argumentos predeterminados

Los parámetros de Kotlin pueden tener valores predeterminados. Donde Kona añade `@JvmOverloads`, Java ve una sobrecarga por parámetro opcional: por ejemplo `Response.text(body)` y `Response.text(body, status)`, o `config.get(key)` y `config.get(key, default)`. Unas pocas funciones no tienen sobrecargas Java, y Java debe pasar cada argumento:

| Llamada | Kotlin | Java |
|------|--------|------|
| Búsqueda de entorno | `Env.get("KEY")` | `Env.get("KEY", null)`, o `Env.getOrDefault("KEY", "x")` |
| Entrada de petición | `request.input("q")` | `request.input("q", null)` |
| URL de ruta con nombre | `router.route("home")` | `router.route("home", Map.of())` |

Si Java informa «method cannot be applied to given types» en una llamada de Kona, un argumento predeterminado ausente es la razón habitual.

## Tipos de retorno genéricos

Las llamadas que buscan por **clave de cadena** devuelven un `T` genérico, inferido de la variable a la que asignas:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val greeter: Greeter = app.container.make("greeter")
val port: Int? = app.config.get("server.port")
```

</TabItem>
<TabItem label="Java">

```java
Greeter greeter = app.getContainer().make("greeter");
Integer port = app.getConfig().get("server.port");
```

</TabItem>
</Tabs>


El cast no está comprobado: si el valor almacenado tiene otro tipo, obtienes un `ClassCastException` donde lo usas. Prefiere los getters tipados de configuración (`getInt`, `getString`, `getBoolean`) y las búsquedas del contenedor por clase (`make(Greeter.class)`) cuando puedas.

## Mezclar ambos lenguajes en un proyecto

Un proyecto Kotlin puede contener clases Java y al revés; a Kona no le importa en qué lenguaje se escribió un proveedor o un controlador. Los andamiajes usan las raíces estándar `src/main/kotlin` y `src/main/java`, así que puedes añadir las fuentes del otro lenguaje junto a las primeras. `grind make:controller` elige `.java` en cuanto existe cualquier archivo `.java` bajo `src/main/java/`; pasa `--lang=` para anularlo.

## Ejemplos de referencia

`samples/hello-kotlin` y `samples/hello-java` en el repositorio de Kona coinciden con la disposición de *código* **web** predeterminada de `kona new` (bienvenida Crema + `/api/health`) con pruebas de humo HTTP. **No** son andamiajes completos: no tienen `./grind` ni `./gradlew` local, y los ejecutas desde la raíz del repositorio (`./gradlew :hello-kotlin:run` / `:hello-java:run`). Para el camino de producto con `./grind serve`, usa [Instalación](../installation/) y [Tu primera app](../first-app/). Otros kits (`api`, `wire`, `inertia`) los cubren las regresiones de `kona new` en la suite de pruebas del CLI.
