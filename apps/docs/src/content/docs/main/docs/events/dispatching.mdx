This page is the full public API for `EventDispatcher` and `EventListener`. For wiring and concepts, start with [Events](/docs/events/). For test doubles, see [Testing](/docs/events/testing/).

## Defining events

An event is any non-null object. There is no required base class or marker interface. Prefer **immutable payloads** with clear fields:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
data class UserRegistered(
    val userId: Long,
    val email: String,
)

data class PaymentFailed(
    val orderId: String,
    val reason: String,
)
```

</TabItem>
<TabItem label="Java">

```java
public final class UserRegistered {
    public final long userId;
    public final String email;

    public UserRegistered(long userId, String email) {
        this.userId = userId;
        this.email = email;
    }
}

public record PaymentFailed(String orderId, String reason) {}
```

</TabItem>
</Tabs>

Keep events free of framework types when you can. Pass identifiers and value objects; let listeners resolve `Mailer`, repositories, or `Bus` from the container if they need services.

## Registering listeners

### `listen(Class, EventListener)`

Adds a handler for exactly that class. Returns `this` so you can chain calls.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
val bus = EventDispatcher()

bus.listen(UserRegistered::class.java) { event ->
    // trailing lambda → EventListener SAM
}

bus.listen(UserRegistered::class.java, EventListener { event ->
    // explicit SAM
})

bus
    .listen(UserRegistered::class.java) { /* A */ }
    .listen(PaymentFailed::class.java) { /* B */ }
```

</TabItem>
<TabItem label="Java">

```java
EventDispatcher bus = new EventDispatcher();

bus.listen(UserRegistered.class, event -> {
    // lambda implements EventListener
});

bus.listen(UserRegistered.class, (EventListener<UserRegistered>) event -> {
    // explicit SAM when the compiler needs help
});

bus
    .listen(UserRegistered.class, event -> { /* A */ })
    .listen(PaymentFailed.class, event -> { /* B */ });
```

</TabItem>
</Tabs>

### Kotlin reified `listen`

```kotlin
inline fun <reified T : Any> listen(listener: EventListener<T>): EventDispatcher
```

```kotlin
bus.listen<UserRegistered> { event ->
    logger.info("user {}", event.userId)
}
```

Java has no reified form — always pass `SomeEvent.class`.

### Listener shape

```kotlin
fun interface EventListener<T : Any> {
    fun handle(event: T)
}
```

Any class (or method reference) that matches `handle` works:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class SendWelcomeEmail : EventListener<UserRegistered> {
    override fun handle(event: UserRegistered) {
        // …
    }
}

bus.listen(UserRegistered::class.java, SendWelcomeEmail())
```

</TabItem>
<TabItem label="Java">

```java
public final class SendWelcomeEmail implements EventListener<UserRegistered> {
    @Override
    public void handle(UserRegistered event) {
        // …
    }
}

bus.listen(UserRegistered.class, new SendWelcomeEmail());
```

</TabItem>
</Tabs>

There is **no** automatic class scanning, no `@Listens` attribute, and no `EventServiceProvider` map of event → listener class names. Registration is always explicit `listen` calls.

## Dispatching

```kotlin
fun dispatch(event: Any)
```

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
bus.dispatch(UserRegistered(userId = 7, email = "a@b.c"))
```

</TabItem>
<TabItem label="Java">

```java
bus.dispatch(new UserRegistered(7, "a@b.c"));
```

</TabItem>
</Tabs>

Behavior:

| Situation | Result |
|-----------|--------|
| Listeners registered for `event.javaClass` | Each `handle` runs in registration order |
| No listeners for that class | Returns immediately; no error |
| A listener throws | Exception propagates; remaining listeners for this dispatch are skipped |
| Dispatch a type with zero registrations | Silent no-op (same as “no listeners”) |

There is no `Event::dispatch` static helper and no top-level `event(...)` function — call `dispatch` on an `EventDispatcher` instance.

### Exact class matching

Matching uses the event instance’s **runtime class**, not interfaces or superclasses:

```kotlin
open class DomainEvent
class OrderShipped : DomainEvent()

bus.listen(DomainEvent::class.java) { /* never runs for OrderShipped */ }
bus.dispatch(OrderShipped()) // no DomainEvent listeners invoked

bus.listen(OrderShipped::class.java) { /* runs */ }
bus.dispatch(OrderShipped())
```

If you need shared handling, register the same listener (or a shared function) on each concrete class, or put shared logic in a helper the concrete listeners call.

### Multiple listeners

```kotlin
bus.listen(OrderShipped::class.java) { audit.log(it) }
bus.listen(OrderShipped::class.java) { mail.sendReceipt(it) }
bus.listen(OrderShipped::class.java) { metrics.increment("orders.shipped") }

bus.dispatch(OrderShipped("42"))
// audit → mail → metrics (registration order)
```

Listeners are stored in a concurrent map of copy-on-write lists — safe to register from multiple threads, but prefer registering during boot before traffic arrives.

## Inspection

| Method | Returns |
|--------|---------|
| `hasListeners(Class<*>)` | `true` when at least one listener is registered for that class |
| `listenerCount(Class<*>)` | Number of listeners for that class (`0` if none) |

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
assertTrue(bus.hasListeners(OrderShipped::class.java))
assertEquals(3, bus.listenerCount(OrderShipped::class.java))
assertEquals(0, bus.listenerCount(PaymentFailed::class.java))
```

</TabItem>
<TabItem label="Java">

```java
assertTrue(bus.hasListeners(OrderShipped.class));
assertEquals(3, bus.listenerCount(OrderShipped.class));
```

</TabItem>
</Tabs>

These do **not** tell you whether a particular `dispatch` already ran; they only describe the registry. For recording dispatches in tests, use [`FakeEvent`](/docs/events/testing/).

## Removing listeners

| Method | Effect |
|--------|--------|
| `forget(Class<*>)` | Removes **all** listeners for that event class |
| `flush()` | Clears **every** listener for every class |

There is no API to remove a single listener instance while leaving others for the same type.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
bus.forget(OrderShipped::class.java)
assertFalse(bus.hasListeners(OrderShipped::class.java))

bus.flush()
// registry empty
```

</TabItem>
<TabItem label="Java">

```java
bus.forget(OrderShipped.class);
bus.flush();
```

</TabItem>
</Tabs>

Use `flush()` between tests when you hold a shared dispatcher, or prefer a fresh `EventDispatcher()` / [`FakeEvent`](/docs/events/testing/) per test.

## Register from the container

Typical production pattern: one singleton bus, listeners attached in `boot`.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
class EventBindings : ServiceProvider {
    override fun register(app: Application) {
        // EventServiceProvider already bound EventDispatcher; nothing here
    }

    override fun boot(app: Application) {
        val events = app.resolve(EventDispatcher::class.java)
        val mailer = app.resolve(Mailer::class.java)

        events.listen(UserRegistered::class.java) { event ->
            mailer.send(/* welcome using event.email */)
        }

        events.listen(OrderShipped::class.java) { event ->
            app.resolve(Bus::class.java).dispatch(SendShipmentNotification(event.id))
        }
    }
}
```

</TabItem>
<TabItem label="Java">

```java
public final class EventBindings implements ServiceProvider {
    @Override
    public void register(Application app) { }

    @Override
    public void boot(Application app) {
        EventDispatcher events = app.resolve(EventDispatcher.class);
        Mailer mailer = app.resolve(Mailer.class);

        events.listen(UserRegistered.class, event ->
            mailer.send(/* welcome using event.email */)
        );

        events.listen(OrderShipped.class, event ->
            app.resolve(Bus.class).dispatch(new SendShipmentNotification(event.id))
        );
    }
}
```

</TabItem>
</Tabs>

Ensure `EventServiceProvider` is registered **before** any provider that resolves `EventDispatcher` in `boot`. Providers that only call `listen` in `boot` are fine as long as `EventServiceProvider` appears earlier in the provider list (or was registered before boot).

## Common use cases

### Decouple a write path from side effects

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
fun checkout(order: Order, events: EventDispatcher) {
    orders.save(order)
    events.dispatch(OrderPlaced(order.id, order.total))
}
```

</TabItem>
<TabItem label="Java">

```java
void checkout(Order order, EventDispatcher events) {
    orders.save(order);
    events.dispatch(new OrderPlaced(order.id, order.total));
}
```

</TabItem>
</Tabs>

Listeners send mail, update search indexes, or enqueue jobs without the checkout method knowing about them.

### Fan-out to a queue job

```kotlin
events.listen(OrderPlaced::class.java) { event ->
    bus.dispatch(ProcessOrderPlaced(event.orderId)) // Job + ShouldQueue
}
```

The event stays synchronous and tiny; the job does the slow work. See [Jobs & dispatch](/docs/queue/jobs/).

### Audit logging

```kotlin
events.listen(PaymentFailed::class.java) { event ->
    logger.warn("payment failed order={} reason={}", event.orderId, event.reason)
}
```

### Grind / steam

From a booted application in [steam](/docs/steam/) or a custom [grind](/docs/grind/creating-commands/) command, resolve the same singleton and dispatch for manual ops:

```kotlin
app.resolve(EventDispatcher::class.java).dispatch(OrderShipped("ops-1"))
```

## API reference

### `EventDispatcher`

| Method | Description |
|--------|-------------|
| `listen(Class<T>, EventListener<T>): EventDispatcher` | Register a listener; chainable |
| `listen<T>(EventListener<T>): EventDispatcher` | Kotlin reified overload |
| `dispatch(Any)` | Invoke listeners for `event.javaClass` in order |
| `forget(Class<*>)` | Drop all listeners for one type |
| `flush()` | Drop all listeners |
| `hasListeners(Class<*>): Boolean` | Whether any listener exists for the type |
| `listenerCount(Class<*>): Int` | Count of listeners for the type |

### `EventListener<T>`

| Method | Description |
|--------|-------------|
| `handle(T)` | Invoked once per matching `dispatch` |

### `EventServiceProvider`

| Method | Description |
|--------|-------------|
| `register(Application)` | `singleton(EventDispatcher::class.java) { EventDispatcher() }` |
| `boot` | Not overridden (no default listeners) |

## Pitfalls

1. **Forgetting the provider.** Resolving `EventDispatcher` without `EventServiceProvider` fails unless you bound it yourself.
2. **Exact type only.** Listening on a base type does not receive subclass dispatches.
3. **Exceptions abort the chain.** A throwing listener skips later listeners for that dispatch; catch inside the listener if you want best-effort fan-out.
4. **Long work on the request thread.** `dispatch` blocks until all listeners finish — move heavy work to [queues](/docs/queue/).
5. **Shared mutable state.** Listeners run on the caller’s thread; keep them thread-safe if you dispatch from many virtual threads.
6. **Cadence vs application events.** Model hooks use `ModelDispatcher`, not `EventDispatcher`. See [Serialization, collections & events](/docs/cadence/serialization-events/#lifecycle-events).
7. **No stop-propagation.** You cannot cancel remaining listeners except by throwing (which surfaces to the publisher).
8. **`forget` is all-or-nothing per type.** You cannot unregister one of several listeners for the same class.

## Not available today (detail)

| Feature | Notes |
|---------|-------|
| Subscribers | No `subscribe(dispatcher)` class that maps many events in one place |
| Queued listeners | No `ShouldQueue` on `EventListener`; use `Bus` from a sync listener |
| After commit | No deferral until a DB transaction commits |
| Discovery | No package scan or KSP index of listeners |
| Facades / helpers | No `Event.dispatch` / `event()` — use the dispatcher instance |
| Wildcards | No `listen("order.*")` on this bus |
| Priority / sorted listeners | Order is registration order only |
| Halt / stop | No return-value or API to stop remaining listeners |

If you need those behaviors, implement them in application code (for example a thin wrapper around `EventDispatcher`) or wait for a future deepen milestone — do not invent APIs that are not in `modules/events`.
