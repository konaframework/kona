Kona uses **two** command-line tools on purpose:

| Tool | Where it lives | What it does |
|------|----------------|--------------|
| **`kona`** | On your PATH (global) | Creates apps (`kona new`) and can proxy to grind (`kona grind …`) |
| **`./grind`** | Inside each app created by `kona new` | Day-to-day work for *that* app: serve, generate controllers, … |

You install `kona` once. Every project from `kona new` ships its own `./grind` (and `grind.bat` on Windows). Prefer `./grind` when you are already in the app directory; from a nested folder (or out of habit) you can also run `kona grind <command>` — it walks upward for a Gradle project and forwards the rest of the line to that app’s grind script.

## Happy path

```bash
# 1. JDK 21+
java -version

# 2. Install the global `kona` CLI (latest Maven Central release)
curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
export PATH="$HOME/.local/bin:$PATH"

# 3. Create an application
kona new my-app --no-interaction
cd my-app

# 4. Serve
./grind serve
```

Open `http://127.0.0.1:4000/`. Supported path: **install `kona` → `kona new` → `./grind serve`**.

Drop `--no-interaction` if you want the installer to ask kit, language, CSS, and database. From a nested folder you can use `kona grind serve` instead of `./grind serve`.

Generated apps resolve `org.konaframework` libraries from **[Maven Central](https://repo1.maven.org/maven2/org/konaframework/)**. You do not need a Kona source checkout to build or run an application.

To ship that app, see [Deployment](../deployment/) (`./grind deploy:systemd`, not `./grind serve`).

## 1. JDK 21+

```bash
java -version   # must report 21 or newer
```

The installer and generated apps use the Gradle wrapper; you do not need a separate Gradle install.

## 2. Install the global `kona` CLI

### Recommended: curl installer

```bash
curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
```

The curl URL only downloads the **installer script** from GitHub. That script then installs the latest **Maven Central** `org.konaframework:kona-cli` release (git tag `vX.Y.Z`) into `~/.kona`, builds the CLI, and links `~/.local/bin/kona`. It does **not** install unreleased commits from `main`.

```bash
export PATH="$HOME/.local/bin:$PATH"    # add this to ~/.bashrc or ~/.zshrc
kona version
kona help
```

Override the install prefix with `KONA_PREFIX` if `~/.local` is not where you keep binaries.

Re-run the same curl command to update to a newer Central release.

| Variable | Default | Meaning |
|----------|---------|---------|
| `KONA_SRC` | `~/.kona` | Where source is cloned / updated |
| `KONA_PREFIX` | `~/.local` | Where `bin/kona` and `lib/kona` are installed |
| `KONA_REF` | latest Central `kona-cli` (`vX.Y.Z`) | Git branch or tag to install |
| `KONA_REPO` | `https://github.com/konaframework/kona.git` | Clone URL |

Example — pin a published tag, or install unreleased `main`:

```bash
KONA_REF=v0.2.0 curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
KONA_REF=main curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
# same as KONA_REF=main:
curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash -s -- --dev
```

:::note[What about package managers?]
Homebrew, SDKMAN, and standalone GitHub Release binaries are not published yet. The curl installer is the supported path. Application dependencies still come from Maven Central under the `org.konaframework` group — that is separate from putting the `kona` CLI on your PATH.
:::

## 3. Create an application

Scripts and CI — no prompts:

```bash
kona new my-app --no-interaction
kona new my-app --lang=java --no-interaction
```

Interactive (asks directory, language, kit, CSS, database):

```bash
kona new
kona new my-app
```

`--no-interaction` uses defaults and never waits. `CI=true` does **not** skip questions — pass the flag. Details: [Starter kits](../../starter-kits/).

`kona new` writes a self-contained Gradle app that already includes:

- `./grind` / `grind.bat` — app-local CLI
- `./gradlew` / `gradlew.bat` — Gradle wrapper
- `src/main/…` layout, `.env`, and starter kit files
- Dependencies on `org.konaframework:…` at the **same version** the installer just installed (latest Maven Central)

You should see a **DONE** chip and next steps ending with `./grind serve`.

Pin another release with `--kona-version=x.y.z` if you need to.

## 4. Work inside the app with `./grind`

```bash
cd my-app
./grind serve
./grind make:controller Post
```

`./grind` is a thin script that runs the project’s Gradle `grind` task with `kona-grind` on the classpath. It is **not** the same binary as global `kona`.

## Dependencies in your app

Generated `build.gradle.kts` files look like a normal Gradle app:

```kotlin
repositories {
    mavenCentral()
}

dependencies {
    implementation("org.konaframework:kona-http:0.2.0")
    implementation("org.konaframework:kona-grind:0.2.0")
    // … other org.konaframework modules for your kit
    // Matches default H2 URL in config/Database:
    runtimeOnly("com.h2database:h2:2.3.232")
}
```

Add packages later with [`./grind install`](../../packages/install/) (for example `./grind install wire` or `./grind install inertia`).

## Contributing to Kona (optional)

This section is for **framework contributors**, not application developers.

### Local CLI from a checkout

```bash
git clone https://github.com/konaframework/kona.git
cd kona
./scripts/install.sh --local
# or: ./scripts/install-kona.sh
```

`--local` builds and links `~/.local/bin/kona` from **that tree** (not the Maven Central release the curl installer uses). `./scripts/install.sh --dev` (or `KONA_REF=main`) installs git `main` without requiring a prior clone. Then `kona version` prints the stamped version plus `git describe`. If `command -v kona` points elsewhere, that other binary is stale.

### Repo samples

The checked-in apps under `samples/hello-kotlin` and `samples/hello-java` are Gradle modules inside the Kona repository (regression and layout reference). They do **not** ship `./grind` or a standalone wrapper — run them from the repository root:

```bash
./gradlew :hello-kotlin:run
./gradlew :hello-java:run
```

To experience the product path (`./grind serve`, generators, Maven Central coordinates), use `kona new` as above.

### Developing against a local framework checkout

If you are changing Kona itself and want an app to pick up unpublished modules:

```bash
# from the Kona checkout — optional local publish
./gradlew publishToMavenLocal -x test

# or point the app at the checkout
./gradlew run -Pkona.home=/path/to/kona
# or: export KONA_HOME=/path/to/kona
```

You do **not** need these steps to try Kona after a normal `kona new`.
