All commands below assume you are in an application directory that contains `./grind` (created by `kona new`). From anywhere under that app you can also run the same commands through the global CLI:

```bash
kona grind serve
kona grind route:list
kona grind migrate
kona grind --help   # explains the proxy; other args are forwarded to ./grind
```

`kona grind` finds the nearest Gradle project (same walk as `./grind serve`), then runs that app’s `./grind` or `grind.bat` with your remaining arguments and exit code.

## `./grind serve`

```bash
./grind serve
./grind serve --host=127.0.0.1 --port=4000
./grind serve --in-process --once
./grind serve --in-process --bootstrap=bootstrap.App
```

| Flag | Effect |
|------|--------|
| `--host` / `--port` | Bind address (also via `.env` as `HOST` / `PORT`) |
| `--in-process` | Load compiled classes and call `bootstrap.App.create` instead of `gradlew run` |
| `--once` | With in-process mode, return after the server starts |
| `--bootstrap=` | Bootstrap class (in-process only) |
| `--base=` | Directory to search upward for the Gradle project |

Default host is **127.0.0.1** and default port is **4000** (also in generated `.env`). If that port is already in use, grind asks whether to try the next one (4001, 4002, …). If no Gradle project is found, grind exits and tells you to run `kona new`.

On start, grind prints a Termwind box with the local URL (for example `http://127.0.0.1:4000`) and how to stop (`Ctrl+C`). Gradle runs with `--quiet --console=plain` so you do not see a forever-stuck build progress bar while the server is running.

`./grind serve` is for **local development**. For production, start `bootstrap.App` via `installDist` / `distZip` (or an equivalent JVM launch) — see [Deployment](../../guides/deployment/).

## `./grind route:list`

```bash
./grind route:list
./grind route:list --json
./grind route:list --method=GET --name=users --path=/api
./grind route:list --compact
./grind route:list --columns=method,uri,name --sort=uri --reverse
```

Boots the application in-process (same as migrate: find the project, load `build/classes`, call `bootstrap.App.create`) and prints every route registered on the shared `Router`. Run `./gradlew classes` first so the compiled app is on the classpath.

The table columns are **Method**, **URI**, **Name**, **Action**, and **Middleware**. Methods are joined with `|` when a route accepts more than one (for example `PUT|PATCH`). Named handler classes show their fully qualified name; Kotlin/Java lambdas show as `Closure`. Route middleware classes show their simple names, comma-separated; lambda middleware shows as `Closure`. Unnamed routes leave the name cell blank.

A footer reports `Showing N route(s)`. When nothing is registered: `Your application doesn't have any routes.` When filters remove everything: `Your application doesn't have any routes matching the given criteria.` Both still exit `0`.

| Flag | Effect |
|------|--------|
| `--json` | Print a JSON array (keys `method`, `uri`, `name`, `action`, `middleware`, `vendor`) instead of the table. `name` is `null` when the route has no name. |
| `--method=` | Keep routes that declare this verb (comma-separated). Case-insensitive. `HEAD` also matches `GET` routes, because the router falls back that way. |
| `--name=` | Keep routes whose name contains this substring (comma-separated, case-insensitive). Unnamed routes never match. |
| `--path=` | Keep routes whose URI contains this substring (comma-separated, case-sensitive). |
| `--except-path=` | Drop routes whose URI contains any of these substrings (comma-separated). |
| `--except-vendor` | Drop routes whose handler class lives under `org.konaframework.` (framework packages). App handlers such as `app.http.ShowUser` stay. Lambdas compiled inside a framework class are treated as vendor. |
| `--only-vendor` | Keep only those vendor handlers. Combined with `--except-vendor`, the table is empty. |
| `--reverse` | Reverse the sort order. |
| `--sort=` | Sort by `method`, `uri` (default), `name`, `action`, or `middleware`. Unknown values exit `1`. |
| `--columns=` | Comma-separated subset of `method`, `uri`, `name`, `action`, `middleware`. Unknown values exit `1`. |
| `--compact` | Shorthand for `--columns=method,uri,action,middleware`. |
| `--bootstrap=` / `--base=` | Same meaning as `serve --in-process`. |

`--json` ignores `--columns` / `--compact` and always emits the full object shape. `--quiet` suppresses the table and the JSON.

If `HttpServiceProvider` was never registered, grind exits `1` with `No Router bound`.

See [Routing](../../http/routing/#listing-routes-with-grind) for how the table maps onto `Router` / `Route`.

## `./grind route:cache` / `./grind route:clear`

```bash
./grind route:cache
./grind route:clear
```

`route:cache` boots the app, then writes a pretty-printed JSON snapshot of the live table to `bootstrap/cache/routes.json` (creates `bootstrap/cache/` as needed). Success: `Routes cached successfully.`

HTTP dispatch does **not** read this file. Route registration already lives in compiled Kotlin/Java (providers and `WebRoutes` / `ApiRoutes`). The snapshot is for inspection, CI, and editor tooling.

`route:clear` deletes `bootstrap/cache/routes.json` if it exists and always prints `Route cache cleared successfully.` It does not boot the application. Missing file is still a successful clear.

Both commands require a Kona app at or above `--base=` (same project walk as `serve`).

## `./grind make:command`

```bash
./grind make:command SendDigest
./grind make:command SendDigest --command=mail:digest --lang=java
```

Generates a `ConsoleCommand` under `app/console/commands/` and registers it in `META-INF/kona/commands`. Full guide: [Creating commands](../creating-commands/).

## `./grind make:controller`

```bash
./grind make:controller Post
./grind make:controller AccountController --lang=java
./grind make:controller Post --resource
./grind make:controller Post --api --requests --model=Post
```

Writes under `src/main/kotlin|java/app/http/controllers/`. Names cannot contain path separators; invalid identifiers are rejected. Language defaults from existing `.java` files under `src/main/java/`, or pass `--lang=`.

| Flag | Effect |
|------|--------|
| `--resource` | `BaseResourceController` subclass with `index` / `create` / `store` / `show` / `edit` / `update` / `destroy` — pass the instance to `router.resource` |
| `--api` | Same subclass, but no `create` / `edit` overrides (the base returns 404). Use with `router.apiResource` |
| `--requests` | Also writes `Store{Model}Request` / `Update{Model}Request`; `store` / `update` call `validate(request, …)` (signatures stay `Request` so they match `ResourceController`) |
| `--model=Name` | Model name used for form-request class names (defaults from the controller name) |

Unlike `serve`, `make:controller` does not walk upward from nested folders unless you pass `--base=`.

## `./grind make:resource`

```bash
./grind make:resource User
./grind make:resource PostResource --collection --lang=java
```

Writes under `src/main/kotlin|java/app/http/resources/`. Names get a `Resource` suffix when missing. Pass `--collection` to include a static/companion `collection` helper that wraps items in `JsonResource.collection(...)`.

## Database commands

These commands work with [Cadence](../../cadence/). Generators write source files; the others boot your application in-process.

| Command | Writes / does |
|---------|---------------|
| `./grind make:model <Name> [-mcrfspaR]` | `app/models/<Name>`; short flags: `-m` migration, `-c` plain controller, `-r` `BaseResourceController` subclass, `-f` factory, `-s` seeder, `-p` policy, `-R` / `--requests` Store/Update form requests, `--api` API resource controller (no create/edit overrides), `-a` / `--all` migration + factory + seeder + resource controller + requests + policy |
| `./grind make:migration <name> [--create=table] [--table=table]` | File `database/migrations/{yyyy_MM_dd_HHmmss}_{snake_name}` with PascalCase class (snake_case or PascalCase input); appends the class to `META-INF/kona/migrations`; `create_x_table` creates `x`, `…_to_x_table` alters `x` |
| `./grind make:factory <Name>Factory [--model=Name]` | `database/factories/<Name>Factory` |
| `./grind make:seeder <Name>Seeder` | `database/seeders/<Name>Seeder` |
| `./grind migrate [--seed] [--class=…] [--seeder=…]` | Runs pending migrations as one new batch (dotted `DONE` rows); with `--seed` / `--seeder` / `--seeder=Class`, also runs a seeder in the same process |
| `./grind migrate:fresh [--seed] [--drop-views] [--drop-types]` | Drops all tables (and optionally views / user types) then runs every migration |
| `./grind migrate:refresh [--step=N] [--seed]` | Reverts all batches (or the last `N`) then migrates again |
| `./grind migrate:rollback [--step=N]` | Reverts the last `N` batches (default 1) |
| `./grind migrate:reset` | Reverts every migration |
| `./grind migrate:install` | Creates the `extract_migrations` bookkeeping table if it is missing |
| `./grind migrate:status` | Table of `Ran` / `Pending`, batch, and migration name |
| `./grind db:wipe [--drop-views] [--drop-types]` | Drops all tables (and optionally views / user types) without migrating |
| `./grind db:seed [--class=…]` | Runs a seeder (default `database.seeders.DatabaseSeeder`) |
| `./grind db:show` | Connection, driver, URL, and a table of table names with column counts |
| `./grind db:table <name>` | Column name, type, nullable, and default for one table |
| `./grind schema:dump [--path=database/schema.sql]` | Writes `CREATE TABLE` SQL reconstructed from JDBC metadata |

All generators accept `--lang=kotlin|java` (default: Java when `app/` already has `.java` files) and `--base=`, and never overwrite an existing file.

The migrate and seed commands:

1. find the project at or above `--base` (default: current directory);
2. load `build/classes` and call `create(String[])` on the bootstrap class (`--bootstrap=`, default `bootstrap.App`), so run `./gradlew classes` first;
3. use the `MigrationRegistry` bound in the application container, or migrations listed in `META-INF/kona/migrations` (written by `make:migration`);
4. use the container's `Database` (registered by `CadenceServiceProvider`), or build one from the `database` config section; `--database=name` selects a named connection.

`migrate:fresh` and `db:wipe` drop **user** tables on that connection (foreign keys disabled, or `CASCADE` on PostgreSQL / Oracle). `--drop-views` also drops views. `--drop-types` drops user-defined types on engines that list them (PostgreSQL enums); it is a no-op on SQLite, H2, and MySQL. Bookkeeping tables such as SQLite's `sqlite_sequence` are not dropped.

`schema:dump` writes portable `CREATE TABLE` statements reconstructed from JDBC metadata. Default path is `database/schema.sql` under the application root.

When `app.env` is `production`, migrate / fresh / refresh / reset / rollback / install / wipe / seed require `--force`. `migrate:status`, `db:show`, `db:table`, and `schema:dump` do not.

Stdout is the grind console only: an info line (`Running migrations.` / `Dropping all tables.` / `Nothing to migrate.` / `Seeding database.`), then one dotted row per migration or seeder (`2000_01_01_000000_create_users_table ........ 12ms DONE`). `migrate:status` prints a **Status** / **Batch** / **Migration** table (`Ran` in green, `Pending` in yellow). Connection-pool dumps, SQL traces, and boot logs stay on the `single` file channel under `storage/logs`. Pass `--verbose` (`-v`) to also print those logs on the console.

Errors (unknown connection, a failing migration, a missing seeder class) print a message and exit with status 1. See [Migrations](../../cadence/migrations/) and [Seeders & factories](../../cadence/seeders-factories/) for the APIs behind these commands.

## `./grind down` / `./grind up`

```bash
./grind down
./grind up
./grind down --base=/path/to/app
```

Maintenance mode. `down` writes `storage/framework/down`; HTTP requests then receive **503 Service Unavailable** until `up` removes the file. The `file` driver is selected by `app.maintenance.driver` in `config/App`.

## `./grind key:generate`

```bash
./grind key:generate
./grind key:generate --show
./grind key:generate --force
./grind key:generate --base=/path/to/app
```

Sets a cryptographically random **application key** in the project `.env` as `APP_KEY=base64:…` (32 raw bytes, Base64-encoded). That value is what encryption, signed cookies, and related features read as `app.key`.

| Flag | Effect |
|------|--------|
| *(none)* | Generate a key and write it to `.env` |
| `--show` | Print a new key to the terminal and **do not** modify files |
| `--force` | Allow overwriting an existing key when `APP_ENV=production` |
| `--base=` | Directory to search upward for the Gradle project (same walk as `serve`) |

### What happens on a normal run

1. Grind finds the application root at or above `--base` (default: current directory).
2. If `.env` is missing but `.env.example` exists, grind copies `.env.example` → `.env` first.
3. A new `base64:…` key is generated (same format as `kona new`).
4. The `APP_KEY=…` line in `.env` is replaced. If that line is missing, grind exits with an error.
5. On success: `Application key set successfully.`

### Existing keys and production

- If `APP_KEY` is **empty**, grind writes the new key with no extra prompt.
- If `APP_KEY` is **already set** and the environment is **not** production (`APP_ENV` from the process environment, or from `.env` when unset in the process), grind overwrites the key.
- If `APP_KEY` is already set and `APP_ENV=production`, grind warns and asks for confirmation. Decline (or a non-interactive “no”) cancels the command. Pass `--force` to skip the prompt.

`--show` always prints a fresh key and never touches `.env`, regardless of production or an existing key.

Rotate carefully: ciphertext and signed cookie payloads produced with the old key will not verify after you change `APP_KEY`. See [Encryption](../../security/encryption/).
