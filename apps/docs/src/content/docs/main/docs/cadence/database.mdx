Cadence talks to relational databases through **JDBC**. A **connection** is a named pool (HikariCP) plus identifier-quoting and query-dialect rules. Models, the query builder, and the `DB` facade all use the **global** `Database` manager that `CadenceServiceProvider` builds from your `database` config.

This page covers configuration depth: every env key, each first-party engine, production vs local defaults, scaffold named connections, and how to plug in a database Cadence does not specialize yet.

## How configuration is loaded

1. Your app registers a `ConfigFile` whose `key()` is `"database"` (scaffold: `config/Database.kt` or `config/Database.java`).
2. `CadenceServiceProvider` calls `Database.fromConfig(app.config)`, binds the manager in the container (`Database` and alias `db`), and on boot calls `setAsGlobal()`.
3. If the `database` section has **no** connections and `DB_URL` is set in the environment (or `.env`), Cadence builds a single connection from `DB_*` variables.

### Connection map keys

| Key | Env equivalent | Meaning |
|-----|----------------|---------|
| `url` | `DB_URL` | JDBC URL (required) |
| `username` | `DB_USERNAME` | Login user |
| `password` | `DB_PASSWORD` | Login password |
| `driver` | `DB_DRIVER` | Engine alias (`sqlite`, `h2`, `mysql`, `mariadb`, `pgsql`, `sqlsrv`, `oracle`) or a JDBC class (`org.sqlite.JDBC`). The scaffold uses aliases; Cadence maps them before opening the pool. Omit or leave blank to let Hikari load the driver from the JDBC URL. |
| `pool_size` / `poolSize` | `DB_POOL_SIZE` | Hikari max pool size (default `10`) |
| `quote_identifiers` / `quoteIdentifiers` | `DB_QUOTE_IDENTIFIERS` | Quote table/column names (default `true`) |

`database.default` may be a **connection name** (`"main"`, `"pgsql"`, …) selected by `DB_CONNECTION`, or rarely an **inline connection map**.

Helper env keys used by the scaffolded named connections (when you do not set a full `DB_URL`):

| Key | Used by |
|-----|---------|
| `DB_HOST` | mysql, mariadb, pgsql, sqlsrv, oracle |
| `DB_PORT` | same |
| `DB_DATABASE` | database / service name |

## Why new apps default to SQLite

`kona new` sets `DB_CONNECTION=sqlite` and puts the SQLite JDBC driver on the classpath (`runtimeOnly("org.xerial:sqlite-jdbc:…")`) so a fresh app runs **without installing a database server**:

```text
jdbc:sqlite:storage/database/database.sqlite
```

- The file lives at **`storage/database/database.sqlite`** (not under `src/.../database`, which holds migrations and seeders).
- Each `./grind` process (migrate, seed, serve) opens the same file, so schema and seed data persist across commands.
- Scaffolds create `storage/database/.gitkeep`; `storage/database/*` is gitignored (SQLite file included).

Use `kona new --database=h2` for file H2 (`storage/database/kona` + `AUTO_SERVER`). Use `jdbc:h2:mem:…` only in **unit tests**.

**Production apps should point `DB_CONNECTION` / `DB_URL` at PostgreSQL, MySQL/MariaDB, or another first-party engine.**

## First-party engines

Cadence ships dedicated query dialects and schema grammars for these engines. **By default** that means dialects, named scaffold connections, BOM coordinates, and `kona new --database=` — not every JDBC JAR on every app classpath.

| Engine | Connection name | Typical JDBC URL | Quoting | Schema notes |
|--------|-----------------|------------------|---------|--------------|
| **SQLite** | `sqlite` | `jdbc:sqlite:storage/database/database.sqlite` (scaffold default) | `"…"` | `INTEGER PRIMARY KEY AUTOINCREMENT`; alter is ADD/DROP column + indexes only |
| **H2** | `main` / `h2` | `jdbc:h2:file:…` (`--database=h2`); `jdbc:h2:mem:…` (tests) | `"…"` | `TEXT` → `CHARACTER VARYING` |
| **MySQL** | `mysql` | `jdbc:mysql://…` | `` `…` `` | `AUTO_INCREMENT`, `LONGTEXT`, `TINYINT(1)` |
| **MariaDB** | `mariadb` | `jdbc:mariadb://…` | `` `…` `` | Same DDL family as MySQL; distinct product detection |
| **PostgreSQL** | `pgsql` | `jdbc:postgresql://…` | `"…"` | Identity IDs, `JSONB`, `DROP INDEX IF EXISTS` |
| **Oracle** | `oracle` | `jdbc:oracle:thin:@//…` | `"…"` | `VARCHAR2`, identity, `NUMBER(1)`, PL/SQL drop-if-exists |
| **SQL Server** | `sqlsrv` | `jdbc:sqlserver://…` | `[…]` | `IDENTITY`, `NVARCHAR`, `DROP INDEX … ON table`, `OFFSET/FETCH` |

Query dialects also cover limit/offset (including SQL Server / Oracle `OFFSET … FETCH`), locks (`FOR UPDATE` / share / SQL Server table hints), date-part helpers, native upsert (`ON CONFLICT`, `ON DUPLICATE KEY`, `MERGE`), and generated-key / returning strategies where the driver supports them.

### Choosing an engine with `kona new`

```bash
kona new shop
kona new shop --database=pgsql
kona new shop --database=h2 --lang=java
```

Accepted values: `sqlite` (**default**), `h2`, `mysql`, `mariadb`, `pgsql` (aliases: `postgres`, `postgresql`, `pg`), `sqlsrv` (aliases: `sqlserver`, `mssql`), `oracle`.

The flag sets `DB_CONNECTION` and `DB_URL`, and adds the matching `runtimeOnly` JDBC coordinate next to SQLite when the engine is not the scaffold default.

### Scaffold named connections

Generated `config/Database` includes maps for `main`, `h2`, `sqlite`, `mysql`, `mariadb`, `pgsql`, `sqlsrv`, and `oracle`. Switch with env (`DB_CONNECTION`, `DB_URL`, credentials). `kona new --database=pgsql` writes both the env and the JDBC `runtimeOnly` coordinate. Changing only `DB_CONNECTION` after a SQLite scaffold is enough for grind: the next `./grind migrate` or `./grind serve` adds the matching JAR to `build.gradle.kts` (or Groovy `build.gradle`) and refreshes `konaClasspath`. Pass `--no-jdbc-install` to skip the write. If grind cannot edit a build file, Cadence prints the `runtimeOnly("org.postgresql:postgresql:…")` line to paste yourself.

```bash
DB_CONNECTION=pgsql
DB_URL=jdbc:postgresql://127.0.0.1:5432/kona
DB_USERNAME=kona
DB_PASSWORD=secret
```

Or rely on host/port/database helpers without a full URL (see the generated config file). After grind writes the `runtimeOnly` coordinate, the same command (or the next `./grind`) picks it up through `konaClasspath`.

### Driver coordinates

Recommended versions are pinned in the version catalog / `kona-bom`. Examples:

```kotlin
dependencies {
    // Always present from kona new (zero-install default):
    runtimeOnly("org.xerial:sqlite-jdbc:3.49.1.0")
    // Added by kona new --database=…, or by grind when you switch DB_CONNECTION:
    runtimeOnly("com.h2database:h2:2.3.232")
    runtimeOnly("org.postgresql:postgresql:42.7.5")
    runtimeOnly("com.mysql:mysql-connector-j:9.2.0")
    runtimeOnly("org.mariadb.jdbc:mariadb-java-client:3.5.2")
    runtimeOnly("com.microsoft.sqlserver:mssql-jdbc:12.8.1.jre11")
    runtimeOnly("com.oracle.database.jdbc:ojdbc11:23.7.0.25.01")
}
```

Models use the global default connection unless the model overrides `connectionName`.

Outside an app (scripts, tests), build a manager and call `setAsGlobal()`:

```kotlin
Database()
    .addConnection("default", ConnectionConfig("jdbc:h2:mem:demo;DB_CLOSE_DELAY=-1;DATABASE_TO_LOWER=TRUE"))
    .setAsGlobal()
```

You can also pass an existing `javax.sql.DataSource` and an explicit `Grammar`:

```kotlin
database.addConnection("raw", myDataSource, Grammar.POSTGRES)
```

## SQLite alter limits

SQLite cannot freely reshape tables the way server engines can. Cadence’s SQLite schema grammar emits **ADD COLUMN**, **DROP COLUMN** (SQLite 3.35+), and index DDL on alter; it does **not** rewrite foreign keys onto an existing table in one `ALTER`. Prefer create-time constraints for SQLite, or rebuild the table in a custom migration when you need a full reshape.

## Adding a database Cadence does not specialize

1. **Query identifier quoting** (`Grammar`) — register a URL prefix with `Grammar.registerUrlPrefix`.
2. **Schema DDL** (`SchemaGrammar`) — subclass and `SchemaGrammar.registerProduct` for the JDBC product name.

`Grammar.forUrl` / `SchemaGrammar.forProduct` pick built-ins first, then registrations. Longest URL prefix wins.

## Transactions and pools

- `DB.transaction { … }` binds one JDBC connection to the current thread; nested work joins the same transaction.
- Pools open **lazily** on first use. `Database.close()` closes open pools; configuration remains so the next query can reconnect.
- `disconnect(name)` closes one named pool without forgetting its config.
