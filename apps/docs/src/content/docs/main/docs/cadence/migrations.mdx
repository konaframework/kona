A **migration** is a small class that changes the structure of the database (create a table, add a column, add an index) and can undo that change. Keeping every structural change in a migration means any copy of the application (a teammate's laptop, CI, production) can build the same schema by running the migrations in order.

## Run order

Cadence records which migrations have run in a table called `extract_migrations`, together with a **batch** number. Every `migrate` run that applies something opens a new batch; `rollback` undoes the most recent batch.

You type a **descriptive name** only — snake_case or PascalCase, no timestamp:

```bash
./grind make:migration create_users_table
./grind make:migration AddStatusToUsersTable
```

grind writes a **file** whose name is UTC `yyyy_MM_dd_HHmmss` plus the snake_case description, and a **PascalCase class** inside that file:

```text
2026_10_20_153950_add_status_to_users_table.kt
└ yyyy_MM_dd_HHmmss (UTC)     └ snake_case description

class AddStatusToUsersTable          ← JVM type: no leading digit, no underscores
@MigrationName("2026_10_20_153950_add_status_to_users_table")
```

The timestamp lives on the **file**, not the class. A JVM class name cannot start with a digit, and editors flag underscores in type names. The supported shape is a named PascalCase class in a differently named file: Kotlin allows a public class there; Java requires the class not to be `public` when the filename does not match, so generated Java migrations are package-private. Discovery still lists the fully qualified class name in `META-INF/kona/migrations` and instantiates it reflectively.

`@MigrationName` records the file stem. That stem is what `Migrator` stores in `extract_migrations` and what `./grind migrate` sorts on, so run order does not depend on how lines happen to be listed in the discovery file. Two different descriptions generated in the same second share the same stamp (`…153950_create_flights_table` and `…153950_add_status_to_users_table`). If that **file** already exists, grind bumps the stamp by one second. If the PascalCase **class** already exists under `database/migrations`, grind refuses — two compilation units cannot declare the same class in package `database.migrations`.

The `kona new` users migration is `2000_01_01_000000_create_users_table` with class `CreateUsersTable`, so it always runs first among timestamped migrations. Names **without** a stamp (a hand-written class, or a leftover from an older layout) keep registration order and run **before** timestamped ones. Legacy class names `M{stamp}_DescriptiveName` still sort by that stamp.

You can still bind a `MigrationRegistry` yourself. Timestamped names in that registry are sorted the same way; untimestamped names keep insertion order.

## Writing a migration

A migration implements `org.konaframework.cadence.migrations.Migration` with two methods. `up` applies the change; `down` reverses exactly what `up` did. Both receive a `Schema`, which runs DDL (table-definition SQL) on the migration's connection. grind generates this class in a timestamped snake_case file and stamps `@MigrationName` with that file stem (the example below matches `2026_10_20_141530_create_posts_table.kt` / `.java`).

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
package database.migrations

import org.konaframework.cadence.migrations.Migration
import org.konaframework.cadence.migrations.MigrationName
import org.konaframework.cadence.schema.Schema

@MigrationName("2026_10_20_141530_create_posts_table")
class CreatePostsTable : Migration {
    override fun up(schema: Schema) {
        schema.create("posts") {
            id()
            foreignId("user_id").constrained().cascadeOnDelete()
            string("title", 200)
            text("body").nullable()
            boolean("published").default(false)
            integer("votes").default(0)
            timestamp("published_at").nullable()
            timestamps()
            softDeletes()
            index("user_id", "published")
        }
    }

    override fun down(schema: Schema) {
        schema.dropIfExists("posts")
    }
}
```

</TabItem>
<TabItem label="Java">

```java
package database.migrations;

import org.konaframework.cadence.migrations.Migration;
import org.konaframework.cadence.migrations.MigrationName;
import org.konaframework.cadence.schema.Schema;

@MigrationName("2026_10_20_141530_create_posts_table")
class CreatePostsTable implements Migration {
    @Override
    public void up(Schema schema) {
        schema.create("posts", table -> {
            table.id();
            table.foreignId("user_id").constrained().cascadeOnDelete();
            table.string("title", 200);
            table.text("body").nullable();
            table.bool("published").withDefault(false);
            table.integer("votes").withDefault(0);
            table.timestamp("published_at").nullable();
            table.timestamps();
            table.softDeletes();
            table.index("user_id", "published");
        });
    }

    @Override
    public void down(Schema schema) {
        schema.dropIfExists("posts");
    }
}
```

</TabItem>
</Tabs>


In Kotlin, the block passed to `create` and `table` has the table definition (a `Blueprint`) as its receiver, so you call `id()` directly. In Java, the lambda receives the `Blueprint` as a parameter (`table -> table.id()`).

Two methods have different names in Java because their Kotlin names are Java keywords: `boolean(name)` is `bool(name)`, and the `default(value)` modifier is `withDefault(value)`.

## The schema DSL

### Table operations

| Call | Effect |
|------|--------|
| `create(table) { … }` | `CREATE TABLE` with the columns, foreign keys, and indexes defined in the block |
| `table(table) { … }` | alters an existing table: add columns, foreign keys, and indexes; drop columns and indexes |
| `drop(table)` | `DROP TABLE` (fails when it does not exist) |
| `dropIfExists(table)` | `DROP TABLE IF EXISTS` |
| `rename(from, to)` | renames a table |
| `hasTable(table)` / `hasColumn(table, column)` | checks the current schema |
| `execute(listOf(sql, …))` | runs raw statements |

### Column types

| Method | SQL type | Notes |
|--------|----------|-------|
| `id()` / `id("key")` | `BIGINT` identity primary key | auto-incrementing |
| `string(name)` / `string(name, length)` | `VARCHAR(255)` / `VARCHAR(length)` | length must be positive |
| `text(name)` | `TEXT` (`CHARACTER VARYING` on H2) | text |
| `longText(name)` | `LONGTEXT` on MySQL; `TEXT` elsewhere (`CHARACTER VARYING` on H2) | unbounded text |
| `json(name)` | `JSON` on MySQL/Postgres; `TEXT` on SQLite; `CHARACTER VARYING` on H2 | JSON documents |
| `integer(name)` | `INTEGER` | |
| `bigInteger(name)` | `BIGINT` | |
| `boolean(name)` (Java: `bool`) | `BOOLEAN` | |
| `timestamp(name)` | `TIMESTAMP` | |
| `foreignId(name)` | `BIGINT` | a key pointing at another table; chain `constrained()` |
| `timestamps()` | `created_at`, `updated_at` | both nullable |
| `softDeletes()` | `deleted_at` | nullable, used by [soft deletes](../models/#soft-deletes) |
| `morphs(name)` / `nullableMorphs` / `uuidMorphs` | `{name}_type` + `{name}_id` (+ index) | polymorphic columns; see [Relations](../relations/#polymorphic-relations) |

Columns are `NOT NULL` unless you call a modifier:

| Modifier | Effect |
|----------|--------|
| `nullable()` | allows `NULL` (`nullable(false)` undoes it) |
| `default(value)` (Java: `withDefault`) | `DEFAULT` literal: strings are quoted, booleans become `TRUE`/`FALSE`, `null` becomes `NULL` |
| `useCurrent()` | `DEFAULT CURRENT_TIMESTAMP` |
| `unique()` | adds a unique index on the column |
| `index()` | adds a plain index on the column |

### Indexes

```kotlin
index("email")                                   // users_email_index
index(listOf("user_id", "created_at"), "posts_timeline")
unique("email")                                  // users_email_unique
unique("team_id", "number")                      // composite
dropIndex("users_email_index")                   // inside table(...)
```

Generated index names are `<table>_<columns>_index` or `<table>_<columns>_unique`.

### Foreign keys

```kotlin
foreignId("user_id").constrained()                    // references users(id)
foreignId("editor_id").nullable().constrained("users").nullOnDelete()
foreign("owner_id").references("id").on("owners").onDelete("restrict").onUpdate("cascade")
```

`constrained()` guesses the table from the column name: `user_id` references `users`. Actions are `cascade`, `set null`, `restrict`, and `no action`; `cascadeOnDelete()` and `nullOnDelete()` are shortcuts. Constraints are named `<table>_<column>_foreign`.

### Altering tables

```kotlin
schema.table("users") {
    string("nickname").nullable()
    foreignId("team_id").nullable().constrained()
    dropColumn("legacy_flag")
}
```

Within one `table` call, Cadence drops indexes first, then drops columns, then adds columns, foreign keys, and indexes.

### SQL dialects

The schema DSL generates standard SQL that H2 and PostgreSQL both accept. The `Schema` picks a `SchemaGrammar` from the JDBC driver's product name; `SchemaGrammar.H2` adjusts the few types that differ. Identifier quoting follows the connection, so `quote_identifiers = false` applies to DDL as well.

## Registering and running migrations

`grind make:migration` and `make:model -m` append each new class to `src/main/resources/META-INF/kona/migrations` (one fully qualified class name per line — `database.migrations.CreatePostsTable`, not the filename). `CadenceServiceProvider` loads that file into a `MigrationRegistry` when the app has not bound one itself, then sorts by `@MigrationName` (the file stem) as described above, so `./grind migrate` runs new migrations without a manual bind.

You can still bind a registry explicitly when you need a custom order or hand-written entries:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
import database.migrations.CreatePostsTable
import database.migrations.CreateUsersTable
import org.konaframework.cadence.migrations.MigrationRegistry

class AppServiceProvider : ServiceProvider {
    override fun register(app: Application) {
        app.container.instance(
            MigrationRegistry::class.java,
            MigrationRegistry(CreateUsersTable(), CreatePostsTable()),
        )
    }

    override fun boot(app: Application) = Unit
}
```

</TabItem>
<TabItem label="Java">

```java
import database.migrations.CreatePostsTable;
import database.migrations.CreateUsersTable;
import org.konaframework.cadence.migrations.MigrationRegistry;

public class AppServiceProvider implements ServiceProvider {
    @Override
    public void register(Application app) {
        app.getContainer().instance(MigrationRegistry.class,
            new MigrationRegistry(new CreateUsersTable(), new CreatePostsTable()));
    }

    @Override
    public void boot(Application app) {}
}
```

</TabItem>
</Tabs>


### The Migrator

`Migrator` applies and reverts registry entries on one connection. `Migrator.using` borrows a connection for the duration of a block:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
import org.konaframework.cadence.migrations.Migrator
import org.konaframework.cadence.migrations.MigrationEvents

val ran = Migrator.using(db.connection(), registry) { it.migrate() }       // names that ran
Migrator.using(db.connection(), registry) { migrator ->
    migrator.pending()        // not run yet, in order
    migrator.status()         // List<MigrationStatus(name, batch)>; status.ran is true when batch != null
    migrator.rollback()       // undo the last batch
    migrator.rollback(3)      // undo the last three batches
    migrator.reset()          // undo everything
    migrator.migrate(object : MigrationEvents {                           // optional start/finish callbacks
        override fun finished(name: String, millis: Long) = Unit
    })
}
```

</TabItem>
<TabItem label="Java">

```java
import org.konaframework.cadence.migrations.Migrator;
import org.konaframework.cadence.migrations.MigrationEvents;

List<String> ran = Migrator.using(db.connection(), registry, Migrator::migrate);
Migrator.using(db.connection(), registry, migrator -> {
    migrator.pending();
    migrator.status();
    migrator.rollback();
    migrator.rollback(3);
    migrator.migrate(new MigrationEvents() {
        @Override public void finished(String name, long millis) {}
    });
    return migrator.reset();
});
```

</TabItem>
</Tabs>


Each migration runs in its own transaction together with its `extract_migrations` record. When `up` or `down` throws, the transaction rolls back and a `MigrationException` names the failing migration; the migrations before it stay applied. (Some databases, H2 among them, commit DDL statements immediately, so a half-finished `up` may leave partial changes there.)

Rolling back a recorded migration that is no longer registered throws `MigrationException("Migration not found: …")`.

## grind commands

All commands run from the application directory. The database commands boot your application **in-process** from its compiled classes (`build/classes`), so run `./gradlew classes` after changing migrations. They use the `MigrationRegistry` bound in the container, plus the bound `Database` (from `CadenceServiceProvider`) or, when none is bound, a `Database` built from the `database` config section (your `config/Database` module).

```bash
./grind make:migration create_flights_table          # snake_case; schema.create("flights") stub
./grind make:migration CreateFlightsTable            # same, PascalCase
./grind make:migration add_gate_to_flights_table     # schema.table("flights") stub
./grind make:migration backfill_data                 # empty up/down
./grind make:migration seats --create=seats          # explicit create
./grind make:migration widen_seats --table=seats     # explicit alter
# optional: supply the stamp yourself
./grind make:migration 2026_10_20_141530_create_gates_table

./grind migrate                          # run pending migrations as a new batch (dotted DONE rows)
./grind migrate --seed                   # migrate, then seed in the same process
./grind migrate --seed --class=database.seeders.UserSeeder
./grind migrate:status                   # Ran/Pending, batch, name
./grind migrate:rollback                 # undo the last batch
./grind migrate:rollback --step=2        # undo the last two batches
./grind migrate:reset                    # undo everything
./grind migrate --database=reports       # a named connection
./grind migrate --bootstrap=bootstrap.App
```

`./grind migrate` prints an info header, then one dotted row per migration (`name …… 12ms DONE`). Pool dumps and SQL traces stay in `storage/logs`; pass `--verbose` to print them on the console as well.

`make:migration` accepts snake_case or PascalCase (and an optional `{stamp}_` / `M{stamp}_` prefix if you need a specific second). It writes `database/migrations/{yyyy_MM_dd_HHmmss}_{snake_name}.kt` (or `.java`, chosen by `--lang=` or by existing `.java` files under `app/`) with a PascalCase class and `@MigrationName`, then appends the class to `META-INF/kona/migrations`. It refuses to overwrite an existing file (bumps the stamp by one second) and refuses a second class with the same PascalCase name.

`./grind make:model Flight --migration` creates the model and a timestamped `CreateFlightsTable` migration together; see [Seeders & factories](../seeders-factories/) for `--factory` and `--seeder`.
