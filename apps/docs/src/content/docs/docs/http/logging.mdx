Kona’s `Log` facade sits on top of SLF4J. Use it from HTTP handlers, jobs, and boot code without wiring a logger by hand.

## Where logs go

When an application boots, Kona attaches a daily rolling file appender to the root logger:

- **File:** `storage/logs/kona.log` (relative to the app base path)
- **Console:** whatever Logback already configured (defaults or your own `logback.xml`) stays in place

Scaffolded apps already include `storage/logs/` (with `.gitkeep`). After `./grind serve` or any boot that calls `Log` / framework loggers, you should see lines in `storage/logs/kona.log`.

| Setting | Config key | Env | Default |
| --- | --- | --- | --- |
| Write to file | `logging.to_file` | `LOG_TO_FILE` | `true` |
| File name | `logging.file` | `LOG_FILE` | `kona.log` (under `storage/logs` unless absolute) |
| Root level | `logging.level` | `LOG_LEVEL` | `info` |

`Kona.create` seeds those config keys from the environment before providers boot. You can still override them in a `ConfigFile` or `.configure { }` callback. Set `LOG_TO_FILE=false` (or `logging.to_file=false`) when you only want the console.

Rolled history uses `kona.yyyy-MM-dd.log` beside the active file (14 days retained).

For advanced layouts, filters, or extra appenders, add a `src/main/resources/logback.xml`. Kona only adds (or refreshes) the `KONA_FILE` appender; it does not replace your console configuration.

## Channels

A **channel** is a named SLF4J logger. Separate noisy domains (`orders`, `billing`) from the default `kona` channel:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
Log.channel("orders").info("Order placed")
Log.setDefaultChannel("api")
Log.info("uses the api channel")
```

</TabItem>
<TabItem label="Java">

```java
Log.channel("orders").info("Order placed");
Log.setDefaultChannel("api");
Log.info("uses the api channel");
```

</TabItem>
</Tabs>

`Log.stack("a", "b")` returns a channel for the first name (a convenience when you already think in “stack” terms).

## Shared context

Attach request-scoped fields once; every subsequent message on a channel includes them until you flush:

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
Log.shareContext(mapOf("requestId" to "r-1", "userId" to 42))
Log.info("Handling checkout")
// message includes {requestId=r-1, userId=42}

Log.channel("orders").with(mapOf("orderId" to 9)).info("charged")
Log.flushSharedContext()
```

</TabItem>
<TabItem label="Java">

```java
Log.shareContext(Map.of("requestId", "r-1", "userId", 42));
Log.info("Handling checkout");
Log.channel("orders").with(Map.of("orderId", 9)).info("charged");
Log.flushSharedContext();
```

</TabItem>
</Tabs>

`withContext` merges values and returns the default channel for chaining. Prefer flushing at the end of each HTTP request (for example in middleware) so context does not leak across virtual threads.

## Errors and the HTTP stack

`DefaultExceptionHandler` logs unexpected failures through `Log.error` unless you install a custom `report` callback — see [Exceptions](../exceptions/).
