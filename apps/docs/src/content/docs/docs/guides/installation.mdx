This page gets your machine ready to build and run Kona applications. By the end you will have a JDK that Kona supports, the Kona libraries available to Gradle, and the **grind** command-line tool installed.

## What you need

| Tool | Version | Why |
|------|---------|-----|
| JDK | **21 or newer** | Kona's HTTP server runs every request on a virtual thread, a JDK 21 feature. |
| Gradle | 8+ (via wrapper) | Builds and runs your application. Projects created by `grind new` include the Gradle wrapper (`./gradlew`), so a global Gradle install is optional. |
| Git | any | Only needed if you build Kona from source (currently the usual path). |

Check your JDK:

```bash
java -version
```

The first line should report version 21 or higher. If you have several JDKs installed, make sure `JAVA_HOME` points at a 21+ installation; Gradle uses it to launch the build. Generated projects also declare a **Java toolchain** of 21, so Gradle will refuse to compile with an older compiler rather than produce a confusing runtime failure.

## The Kona artifacts

Kona is published as a set of Maven artifacts under the group **`dev.kona`**. Each artifact is a module you add as a normal Gradle dependency.

| Artifact | Contents | Depends on |
|----------|----------|------------|
| `dev.kona:kona-core` | `Kona` entry point, `Application`, `ServiceProvider`, `Container`, `Config`, `Env`, `Log` | SLF4J (with Logback at runtime), Jackson |
| `dev.kona:kona-http` | `Router`, `HttpKernel`, `Middleware`, `Request`, `Response`, validation, `KonaHttpServer` | `kona-core` |
| `dev.kona:kona-grind` | The grind command-line tool | `kona-http` |

Most applications declare only `kona-http`; Gradle pulls in `kona-core` automatically.

## Getting the artifacts from source

While Kona is pre-1.0, the reliable way to obtain the artifacts is to build them from the repository and publish them to your **local Maven repository** (`~/.m2/repository`), which is what `mavenLocal()` in the build file above reads.

```bash
git clone https://github.com/konaframework/kona.git
cd kona
./gradlew :kona-core:publishToMavenLocal :kona-http:publishToMavenLocal
```

The published version is the one declared as `kona.version` in the repository's `gradle.properties` (currently `0.1.0-SNAPSHOT`). Use the same version string in your application's dependency.

### Alternative: build against a checkout directly

If you are changing Kona itself while working on an app, you can skip publishing. Projects generated by `grind new` contain a hook in `settings.gradle.kts` that includes a Kona checkout as a *composite build*, so Gradle compiles Kona from source and substitutes it for the `dev.kona` dependencies:

```bash
./gradlew run -Pkona.home=/path/to/kona
# or
export KONA_HOME=/path/to/kona
./gradlew run
```

The Gradle property `kona.home` wins over the `KONA_HOME` environment variable. When neither is set, the artifacts come from `mavenLocal()` and then Maven Central.

## Installing grind

grind is a regular JVM application. From the Kona checkout you can run it through Gradle without installing anything:

```bash
./gradlew :kona-grind:run --args="--help"
```

For daily use, build its distribution and put the launcher on your `PATH`:

```bash
./gradlew :kona-grind:installDist
# The launcher script is generated under modules/grind/build/install/kona-grind/bin/
ln -s "$PWD/modules/grind/build/install/kona-grind/bin/kona-grind" ~/.local/bin/grind
grind --help
```

On Windows, add `modules\grind\build\install\kona-grind\bin` to `PATH` and call `kona-grind.bat` (or create a `grind.bat` wrapper). The help output lists the available commands:

```text
Kona grind

Usage:
  grind serve [--host=127.0.0.1] [--port=8080] [--base=.]
              [--in-process [--bootstrap=bootstrap.App] [--once]]
  grind new <name> [--lang=kotlin|java] [--kona-version=x.y.z]
  grind make:controller <Name> [--lang=kotlin|java] [--base=.]
  grind help
```

grind stamps its own Kona version into projects it creates, so a grind built from a given checkout generates apps that depend on that same version. Pass `--kona-version=…` to `grind new` to override it.

## Environment files

Kona reads settings such as the application name and debug mode from **environment variables**. During development it is convenient to keep them in a `.env` file at the root of your project (the **base path**). Projects generated by grind start with:

```bash
APP_NAME=my-app
APP_ENV=local
APP_DEBUG=true
HOST=127.0.0.1
PORT=8080
```

Two rules matter from day one:

- **Process variables win.** If a variable is set in the real environment (by your shell, CI, a container runtime), Kona uses that value and ignores the `.env` line. Production can therefore inject secrets without editing or shipping the file.
- **Debug is off unless enabled.** `APP_DEBUG` defaults to `false`. It accepts `true`/`false`, `1`/`0`, `yes`/`no`, and `on`/`off` in any letter case. With debug on, error responses include the exception message and class name, so never enable it on a public server.

Keep `.env` out of version control for anything that holds secrets. [Config & env](../../concepts/config/) covers the file format and precedence in detail.

## Troubleshooting

- **`Could not find dev.kona:kona-http:…`** — Gradle could not locate the artifact. Run the `publishToMavenLocal` command above, check that the version in your build file matches `kona.version`, or use `-Pkona.home`.
- **`Unsupported class file major version`** or toolchain errors — Gradle is running on a JDK older than 21. Point `JAVA_HOME` at JDK 21+.
- **`grind: command not found`** — the launcher is not on `PATH`. Re-run `installDist` and check the symlink target.
- **`Permission denied: ./gradlew`** — restore the executable bit with `chmod +x gradlew`.
