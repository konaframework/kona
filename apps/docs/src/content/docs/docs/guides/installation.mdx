Kona uses **two** command-line tools on purpose:

| Tool | Where it lives | What it does |
|------|----------------|--------------|
| **`kona`** | On your PATH (global) | Creates new applications: `kona new my-app` |
| **`./grind`** | Inside each app created by `kona new` | Day-to-day work for *that* app: serve, generate controllers, … |

You install `kona` once. Every project from `kona new` ships its own `./grind` (and `grind.bat` on Windows) — you do not install grind globally.

## Happy path

```bash
# 1. JDK 21+ on your PATH
java -version

# 2. Install the global `kona` CLI (fetches source, builds, links ~/.local/bin/kona)
curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash

# 3. Create an application
kona new my-app
cd my-app

# 4. Serve with the app-local CLI
./grind serve
```

Open `http://127.0.0.1:8080/`. That is the supported path: **install `kona` → `kona new` → `./grind serve`**.

## 1. JDK 21+

```bash
java -version   # must report 21 or newer
```

The installer and generated apps use the Gradle wrapper; you do not need a separate Gradle install.

## 2. Install the global `kona` CLI

### Recommended: curl installer

```bash
curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
```

That script prints a colored step progress (JDK → fetch → build CLI → publish libraries → link), syncs source into `~/.kona` (override with `KONA_SRC`), builds `:kona-cli:installDist`, **publishes all `dev.kona` jars to `~/.m2` (`mavenLocal`)**, then installs under `~/.local/lib/kona` with a symlink at `~/.local/bin/kona` (override prefix with `KONA_PREFIX`). It also records the checkout path in `~/.config/kona/home` so `kona new` can set `kona.home` on new apps (`includeBuild`). Set `NO_COLOR=1` to disable ANSI styling.

:::important[Why publish?]
Generated apps depend on `dev.kona:…:0.1.0-SNAPSHOT` from `mavenLocal()` / Maven Central. Those SNAPSHOT jars are not on Central yet — the installer must publish them locally so `./grind serve` can resolve transitive modules such as `kona-filesystem` and `kona-support`.
:::

Ensure `~/.local/bin` is on your `PATH`, then check:

```bash
kona version
kona help
```

Re-run the same curl command (or `~/.kona/scripts/install.sh`) to update.

| Variable | Default | Meaning |
|----------|---------|---------|
| `KONA_SRC` | `~/.kona` | Where source is cloned / updated |
| `KONA_PREFIX` | `~/.local` | Where `bin/kona` and `lib/kona` are installed |
| `KONA_REF` | `main` | Git branch or tag to install |
| `KONA_REPO` | `https://github.com/konaframework/kona.git` | Clone URL |

Example — install a specific ref into a custom prefix:

```bash
KONA_REF=main KONA_PREFIX=$HOME/.local \
  curl -fsSL https://raw.githubusercontent.com/konaframework/kona/main/scripts/install.sh | bash
```

:::note[What about package managers?]
Homebrew, SDKMAN, and standalone GitHub Release binaries are not published yet. The curl installer is the supported path. Framework libraries still publish under the `dev.kona` Maven group for *applications* to depend on — that is separate from putting the `kona` CLI on your PATH.
:::

### Framework contributors (local checkout)

If you already have the repository cloned and are hacking on Kona itself:

```bash
git clone https://github.com/konaframework/kona.git
cd kona
./scripts/install.sh --local
# or: ./scripts/install-kona.sh
```

`--local` builds from that tree and does not fetch into `~/.kona`.

## 3. Create an application

```bash
kona new my-app                 # Kotlin (default)
kona new my-app --lang=java
```

`kona new` writes a self-contained Gradle app that already includes:

- `./grind` / `grind.bat` — app-local CLI
- `./gradlew` / `gradlew.bat` — Gradle wrapper
- `src/main/…` layout, `.env`, and starter kit files

You should see a hint ending with `./grind serve`.

## 4. Work inside the app with `./grind`

```bash
cd my-app
./grind serve
./grind make:controller Post
```

`./grind` is a thin script that runs the project’s Gradle `grind` task with `kona-grind` on the classpath. It is **not** the same binary as global `kona`, and it is **not** something you copy from the Kona monorepo by hand.

## Trying the repo samples

The checked-in apps under `samples/hello-kotlin` and `samples/hello-java` are **monorepo Gradle modules** used for regression and layout reference. They intentionally:

- do **not** ship `./grind` or their own `./gradlew`
- depend on sibling `project(":kona-…")` modules instead of Maven coordinates
- are run from the **Kona repository root**

```bash
# from the Kona checkout root
./gradlew :hello-kotlin:run
./gradlew :hello-java:run
```

To experience the product path (`./grind serve`, generators, a standalone wrapper), use `kona new` as above. Do not expect `./grind` inside `samples/` — those directories are not full scaffolds.

## Optional: local Kona sources while developing the framework

Generated apps depend on `dev.kona:kona-http`, `dev.kona:kona-grind`, and related artifacts from `mavenLocal()` / Maven Central. If you are changing Kona itself:

```bash
# from the Kona checkout
./gradlew :kona-core:publishToMavenLocal :kona-http:publishToMavenLocal :kona-grind:publishToMavenLocal
```

Or point the app at a checkout:

```bash
./gradlew run -Pkona.home=/path/to/kona
# or: export KONA_HOME=/path/to/kona
```

You do **not** need these steps just to try Kona after a normal `kona new`.
