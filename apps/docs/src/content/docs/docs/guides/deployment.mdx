This page is the **production runbook** for an app created with `kona new`. Local development stays on [Your first app](../first-app/) (`./grind serve`). Production is a different launcher: a long-lived JVM process that boots `bootstrap.App` and listens on `HOST`:`PORT`.

**Preferred path on a VM:** systemd. One grind command builds a production-ready directory; `install.sh` copies it into place, writes the unit and environment file, and starts the service.

For many instances, connection pools, Redis, and workers, continue with [Scaling](../scaling/).

## Preferred: systemd in one command

On a machine with **JDK 21** (your laptop, CI, or the server):

```bash
cd hello-kona
./grind key:generate          # once; copy APP_KEY into the generated env file
./gradlew check               # optional, but run it before you ship
./grind deploy:systemd
# Vite / Inertia / Brew kits only, before deploy:systemd:
# npm ci && npm run build
```

That writes:

```text
build/deploy/systemd/hello-kona/
  bin/hello-kona          # start script (from ./gradlew installDist)
  lib/                    # application JAR + dependencies
  public/                 # HTTP document root (do not ship public/hot)
  storage/                # empty writable dirs (logs, framework, app/public, database)
  hello-kona.service      # systemd unit
  hello-kona.env          # production environment (APP_ENV, HOST, PORT, DB_*, …)
  install.sh              # copies the tree, installs the unit, starts the service
  README.txt
```

`./grind deploy:systemd` runs `./gradlew installDist` unless you pass `--skip-build`. Review `hello-kona.env` (especially `APP_KEY` and `DB_*`). Copy the directory to the server, then:

```bash
sudo ./install.sh
```

Default locations on the server:

| Path | What |
|------|------|
| `/var/www/hello-kona/bin/` | start script |
| `/var/www/hello-kona/lib/` | JARs |
| `/var/www/hello-kona/public/` | static files |
| `/var/www/hello-kona/storage/` | writable runtime (must stay writable by the service user) |
| `/etc/kona/hello-kona.env` | environment (mode `0600`; `install.sh` will not overwrite an existing file) |
| `/etc/systemd/system/hello-kona.service` | unit |

`install.sh` creates the `kona` system user if it is missing, runs `systemctl enable --now hello-kona`, and prints status. Probe the process:

```bash
curl -fsS http://127.0.0.1:4000/api/health
# {"status":"ok"}
```

From a checkout that still has `./grind`, run migrations against the same `DB_*` values **before** or as you start traffic:

```bash
./grind migrate --force
```

Substitute `hello-kona` with the directory name you passed to `kona new` (`rootProject.name`).

## Build steps (what the command does)

1. **Find the application root** (same walk as `./grind serve`: `settings.gradle.kts` / `build.gradle.kts`).
2. **Compile a start script** with `./gradlew installDist` → `build/install/<app>/{bin,lib}`.
3. **Assemble the bundle** under `build/deploy/systemd/<app>/`:
   - copy `bin/` and `lib/`
   - copy `public/` (skips `public/hot` and symlinks such as `public/storage`)
   - create empty `storage/{logs,framework,app/public,database}`
   - write `<app>.env` from `.env` (or `.env.example`) with a production overlay
   - write `<app>.service` with `ExecStart=/var/www/<app>/bin/<app> --base=/var/www/<app>`
   - write `install.sh` (executable) and `README.txt`
4. **You** review the env file, copy the bundle, run `sudo ./install.sh`.

`--base=` is how `Kona.create` locates `public/`, `storage/`, and config. The unit always passes it so the working directory and the files stay aligned.

### Flags

```bash
./grind deploy:systemd
./grind deploy:systemd --skip-build          # reuse an existing installDist tree
./grind deploy:systemd --force               # overwrite the output directory
./grind deploy:systemd --output=/tmp/hello-kona
./grind deploy:systemd --prefix=/opt/hello-kona
./grind deploy:systemd --user=www --group=www
./grind deploy:systemd --host=127.0.0.1 --port=4000
./grind deploy:systemd --url=https://app.example.com
./grind deploy:systemd --name=hello-kona
./grind deploy:systemd --java-opts='-XX:+UseG1GC -XX:MaxRAMPercentage=75.0'
```

| Flag | Default | Effect |
|------|---------|--------|
| `--skip-build` | off | Do not run `installDist` |
| `--force` | off | Replace `build/deploy/systemd/<app>/` if it already exists |
| `--output=` | `build/deploy/systemd/<app>` | Bundle directory |
| `--prefix=` | `/var/www/<app>` | Server install root (`WorkingDirectory` / `--base`) |
| `--user=` / `--group=` | `kona` | systemd `User` / `Group` (`install.sh` creates the user) |
| `--host=` / `--port=` | from `.env`, else `127.0.0.1`:`4000` | Bind address written into the env file |
| `--url=` | from `.env`, else `http://<host>:<port>` | `APP_URL` |
| `--name=` | `rootProject.name` | Unit, env file, and directory name |
| `--java-opts=` | G1 + `MaxRAMPercentage=75` | `JAVA_OPTS` on the unit |
| `--base=` | current directory | Application root to search upward from |

Override install destinations at runtime:

```bash
sudo PREFIX=/opt/hello-kona ENV_DST=/etc/kona/hello-kona.env UNIT_DST=/etc/systemd/system/hello-kona.service ./install.sh
```

Java apps use the same command (`./grind deploy:systemd` from a `kona new --lang=java` tree).

## The unit and the env file

`install.sh` installs this shape (generated; names follow `--name`):

`/etc/kona/hello-kona.env`:

```bash
APP_ENV=production
APP_DEBUG=false
APP_URL=https://app.example.com
APP_KEY=base64:…
HOST=127.0.0.1
PORT=4000
LOG_TO_FILE=true
DB_URL=jdbc:postgresql://127.0.0.1:5432/kona
DB_USERNAME=kona
DB_PASSWORD=…
JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
```

`/etc/systemd/system/hello-kona.service`:

```ini
[Unit]
Description=Kona hello-kona
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kona
Group=kona
WorkingDirectory=/var/www/hello-kona
EnvironmentFile=/etc/kona/hello-kona.env
Environment=JAVA_OPTS=-XX:+UseG1GC -XX:MaxRAMPercentage=75.0
ExecStart=/var/www/hello-kona/bin/hello-kona --base=/var/www/hello-kona
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGTERM
LimitNOFILE=65535
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload          # install.sh already does this
sudo systemctl enable --now hello-kona
sudo systemctl status hello-kona
sudo journalctl -u hello-kona -f
```

`install.sh` does **not** overwrite `/etc/kona/hello-kona.env` if that file already exists, so a second deploy keeps production secrets. New keys still go into the bundle’s `hello-kona.env` for you to merge by hand.

## Local vs production

| | Local | Production |
|---|--------|------------|
| Command | `./grind serve` | `bin/<app> --base=<prefix>` (systemd `ExecStart`) |
| `APP_ENV` | `local` | `production` |
| `APP_DEBUG` | `true` | `false` |
| Database | SQLite file under `storage/` (scaffold default) | PostgreSQL, MySQL, MariaDB, SQL Server, or Oracle — not SQLite/H2 |
| Process manager | your terminal | **systemd** (preferred); Docker or a platform that sets `PORT` |
| TLS | optional | reverse proxy / load balancer |

`./grind` remains the tool for **one-off ops** on a checkout (`migrate`, `key:generate`, `deploy:systemd`). It is not the HTTP process you supervise.

## Environment variables

The process environment wins over a `.env` file. systemd injects `/etc/kona/<app>.env` via `EnvironmentFile`, so the file **is** the process environment. Do not commit it.

| Variable | Production | Notes |
|----------|------------|--------|
| `APP_ENV` | `production` | Required for production behavior |
| `APP_DEBUG` | `false` | Turns off exception pages |
| `APP_KEY` | `base64:…` | Encryption / signed cookies. Create with `./grind key:generate` on a trusted machine |
| `APP_URL` | `https://app.example.com` | Public URL used in links |
| `HOST` | `127.0.0.1` behind a local proxy; `0.0.0.0` in Docker / PaaS | Bind address |
| `PORT` | `4000` or the platform’s `PORT` | Listen port |
| `DB_CONNECTION` | `pgsql`, `mysql`, … | Must match `config/Database` |
| `DB_URL` | JDBC URL | Example: `jdbc:postgresql://db:5432/kona` |
| `DB_USERNAME` / `DB_PASSWORD` | credentials | Prefer the env file, not git |
| `DB_POOL_SIZE` | start at `10` | Hikari max size; see [Scaling](../scaling/) |
| `LOG_LEVEL` | `info` | |
| `LOG_TO_FILE` | `true` on VMs with disk; `false` when the platform captures stdout | |
| `JAVA_OPTS` | G1 + 75% RAM | Also set on the unit |

Generate a key:

```bash
./grind key:generate
./grind key:generate --force    # production, key already set
```

## Database and migrations

Point `DB_URL` at a real server database. Run migrations from a checkout that still has `./grind`:

```bash
export DB_URL='jdbc:postgresql://db.internal:5432/kona'
export DB_USERNAME=kona
export DB_PASSWORD=…
./grind migrate --force
```

Typical split:

- **VM (systemd):** copy the bundle, `sudo ./install.sh`, migrate from CI or a checkout with the same `DB_*`, then `systemctl restart <app>` if the process was already running.
- **Container:** run `./grind migrate` in CI (or a one-shot JDK job) against the production database, then roll out the image.

`storage/` must stay writable by the service user (`install.sh` `chown`s the prefix).

Engine list and JDBC URLs: [Database](../../cadence/database/).

## Reverse proxy and TLS

The JVM speaks **HTTP**. Terminate TLS in Caddy, nginx, Traefik, or the cloud load balancer. Bind the app to `127.0.0.1` when the proxy is on the same host.

**Caddy** (certificates included):

```text
app.example.com {
    reverse_proxy 127.0.0.1:4000
}
```

**nginx:**

```nginx
upstream kona_app {
    server 127.0.0.1:4000;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    location / {
        proxy_pass http://kona_app;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;
    }
}
```

Behind a proxy, enable trusted forwarded headers in `bootstrap.Middleware` so `APP_URL`, redirects, and client IP match the public request: `.trustProxies(at = listOf("*"))` and `.trustHosts(at = listOf("app.example.com"))` (Java: `List.of(...)`). Details: [Kernel & server](../../http/kernel-server/).

Use `HOST=0.0.0.0` when the platform routes to the container port.

## Health and static files

```http
GET /api/health → {"status":"ok"}
```

HTTP 200 means the process is up and the kernel answered. It does **not** check the database. Add your own readiness route if you need that.

`GET`/`HEAD` under `public/` (including `/build/assets/…` after a Vite production build) are served from disk. Do not ship `public/hot` — `deploy:systemd` already skips it. That file selects the Vite dev server.

```bash
# Vite / Inertia / Brew kits, in CI or on the build machine, before deploy:systemd
npm ci && npm run build
```

## Alternative: Docker

There is no published Kona runtime image. Use a two-stage build in **the app repo**. Replace `hello-kona` with `rootProject.name`. Prefer systemd on a VM you own; use this when the target is a container platform.

```dockerfile
# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew installDist --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/build/install/hello-kona/ /app/
COPY --from=build /src/public /app/public
RUN mkdir -p /app/storage/logs /app/storage/framework /app/storage/app/public \
    && chown -R 65534:65534 /app/storage
ENV HOST=0.0.0.0 PORT=4000 APP_ENV=production APP_DEBUG=false LOG_TO_FILE=false
EXPOSE 4000
USER 65534:65534
CMD ["/app/bin/hello-kona", "--base=/app"]
```

```bash
docker build -t hello-kona:latest .
docker run --rm -p 4000:4000 \
  -e APP_KEY=base64:… \
  -e APP_URL=https://app.example.com \
  -e DB_URL=jdbc:postgresql://db:5432/kona \
  -e DB_USERNAME=kona \
  -e DB_PASSWORD=… \
  hello-kona:latest
```

Mount a volume on `/app/storage` if you need logs or local disks to survive restarts. Any platform that injects `PORT` works: the scaffold reads it.

## CI (GitHub Actions)

Put this in the **application** repository. The artifact is the systemd bundle (or `installDist` if you only need `bin/` + `lib/`).

```yaml
name: build
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
      - name: Tests
        run: ./gradlew check
      - name: systemd bundle
        run: ./grind deploy:systemd --force
      # Vite kits only:
      # - uses: actions/setup-node@v4
      #   with: { node-version: "22" }
      # - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: hello-kona-systemd
          path: build/deploy/systemd/hello-kona
```

Promote the artifact, merge `/etc/kona/<app>.env` if needed, run migrations, then `sudo ./install.sh` or `systemctl restart <app>`.

## Manual `installDist` (no systemd)

If you are not on systemd, the same start script is:

```bash
./gradlew installDist
./build/install/hello-kona/bin/hello-kona --base=/var/www/hello-kona
```

Ship a zip with `./gradlew distZip` (`build/distributions/hello-kona-<version>.zip`). Unpack, place `public/` and `storage/` next to `bin/` / `lib/`, and start with `--base=` pointing at that folder.

`./gradlew run` starts the same `main`. Prefer `installDist` or `deploy:systemd` on long-lived machines.

## Checklist

1. JDK 21 in CI / on the build host  
2. `./gradlew check` green  
3. `./grind key:generate` (real `APP_KEY`)  
4. Vite kits: `npm run build`  
5. `./grind deploy:systemd` — review `<app>.env` (`APP_ENV=production`, `APP_DEBUG=false`, `APP_URL`, `DB_*`)  
6. Copy the bundle; `sudo ./install.sh`  
7. `./grind migrate --force`  
8. Reverse proxy + `trustProxies` / `trustHosts`  
9. `GET /api/health` returns `{"status":"ok"}`  
10. Heavy load: [Scaling](../scaling/)
