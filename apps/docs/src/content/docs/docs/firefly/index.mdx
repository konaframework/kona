**Kona Firefly** (short name **Firefly**) is the panel you give the people who run an application. A panel is one area of the site: a brand, a navigation tree, and the screens that list and edit records.

You describe those screens in Kotlin or Java. Firefly renders the HTML on the server. Buttons, dialogs, and live fields stay in the browser through [Wire](/docs/wire/) and Alpine. You do not hand-write a new template every time you add a column or a button.

You use a panel when the work is “open the desk, find the order, change it, and see that it saved.” A public marketing page or a JSON API stays on an ordinary Kona route. Adding the Firefly module does not rewrite routes you already defined. Routes appear when a `Panel` calls `mount`.

The same pieces work outside a full panel. A schema, a form, or a table can `render()` to HTML that you put in a view or assert in a test. The panel is what turns those pieces into URLs, a sidebar, and a sign-in screen.

## What you can build

A panel class named `Panel` lives in `app/firefly`. It discovers three folders next to itself:

| Folder | What you put there |
|--------|--------------------|
| `pages/` | Screens you design yourself, such as a desk |
| `widgets/` | Stats, charts, and other blocks on a page |
| `resources/` | One class per record type, such as notes or orders |

The hello samples (`samples/hello-kotlin` and `samples/hello-java`) are that layout, mounted at `/admin`. These guides follow the Kotlin sample. The same screens exist in the Java sample.

On that app you can open:

- `/` — the welcome page, outside the panel
- `/admin/desk` — a custom Desk page, with a form, an infolist, a table, a header action, and a widget
- `/admin/notes/manage` — a simple resource: one page, and create, edit, view, and delete open in a dialog
- `/admin/orders/list`, `/admin/orders/create`, `/admin/orders/edit`, `/admin/orders/view` — a full resource, plus a relation manager for line items on edit and view

You register a panel, then drop a resource in its `resources/` folder. Discovery picks it up. You do not register each page by hand unless you want to.

## Packages

`org.konaframework:kona-firefly` is the panel. It brings the other Firefly modules with it, so an application depends on that one coordinate. The modules split like this, so you can see where a type lives:

- `kona-firefly` — the panel, pages, resources, navigation, tenancy, plugins, import and export, and `Firefly.test`
- `kona-firefly-schemas` — the component tree and its state map. Sections, grids, tabs, and plain text live here
- `kona-firefly-forms` — fields on that tree, including the combobox select and the crafted date picker, with validation
- `kona-firefly-infolists` — read-only entries: text, icons, images, and the other ways to show a record
- `kona-firefly-tables` — columns, filters, search, sort, and pages
- `kona-firefly-actions` — a button or a link, the dialog it can open, and the server method it calls
- `kona-firefly-notifications` — a toast, a database bell, and a broadcast refresh marker
- `kona-firefly-widgets` — stats, charts, and custom blocks on a page
- `kona-firefly-support` — the dialog, icons, theme tokens, and `FireflyException`. The other modules depend on it. You do not add this coordinate yourself

## Plugins

A plugin is a class you pass to `plugin(...)`. `register` runs immediately and `boot` runs when the panel mounts. Inside those methods you call the same panel methods the application calls: a brand, a hook, a page. There is no registry. If the behavior belongs to one app, keep the class in that app. Read [Plugins](/docs/firefly/plugins/).

## Appearance

The shipped look is `KonaTheme`. Colors and type are tokens, and `Stylesheet.render` writes them as CSS custom properties on `.ff-panel`. Component rules only match inside that class, so a page that never renders a panel does not pick up Firefly’s buttons or sidebar.

To change the look, implement `FireflyTheme` and pass it to `theme(...)`. `extraCss()` is wrapped in `.ff-panel { ... }`, so your overrides stay inside the panel. The hello sample’s desk is the shipped theme. Read [Themes and CSS](/docs/firefly/themes/).

## Testing

`Firefly.test` reads HTML you already rendered and checks that a page, a field, a table, or a dialog is there. It lives in `org.konaframework.firefly.testing`.

<Tabs syncKey="lang">
<TabItem label="Kotlin">

```kotlin
Firefly.test(page)
    .assertSee("Ada")
    .assertFormField("name")
    .assertTable("Ada")
    .assertDialog("Export")
```

</TabItem>
<TabItem label="Java">

```java
Firefly.test(page)
    .assertSee("Ada")
    .assertFormField("name")
    .assertTable("Ada")
    .assertDialog("Export");
```

</TabItem>
</Tabs>

`assertSee` fails when the text is missing. `assertFormField` looks for `data-ff-path`. `assertTable` wants both `ff-table` and the text. `assertDialog` wants both `ff-dialog` and the title. `Firefly.test(html)` asserts against a string. The same assertions are listed on [Import and export](/docs/firefly/import-export/).

## How to read the rest

Follow the sidebar from top to bottom the first time:

1. [Requirements](/docs/firefly/requirements/) — JDK and the Kona app you already have.
2. [Installation](/docs/firefly/installation/) — `kona new --kit=firefly`, or add the module to an existing app.
3. [Register a panel](/docs/firefly/registration/) — the `Panel` file, the folders, and `discover`.
4. [A working app](/docs/firefly/working-app/) — a simple notes resource and a full orders resource.

After that, each piece has its own page: what it is, why you would use it, the smallest example, then the methods and the edges. Start with [Panel](/docs/firefly/panel/) when you are ready to leave the walkthrough.

Kotlin and Java call the same types. Examples are shown in both languages, in tabs. The class you extend is `Panel`. The package is `org.konaframework`.
